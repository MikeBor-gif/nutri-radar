# Nutri Radar

Разбор состава пищевых продуктов: нормализация грязных многоязычных списков
ингредиентов, поиск скрытых форм сахара и добавок, предсказание оценки качества
питания по одному тексту состава, ответы на вопросы по базе со ссылками на
конкретные штрихкоды.

> **Инструмент прозрачности состава, а не медицинский или диетологический
> советчик.** Система показывает, что написано в составе, и ссылается на данные.
> Она не даёт рекомендаций по питанию, не строит диеты, не считает нормы под
> человека и не персонализируется под заболевания или цели по весу.
>
> Данные краудсорсинговые и могут быть неполными или неверными.

**Статус: проект закрыт.** Все семь майлстоунов пройдены, три из них
частично — и это окончательное состояние, а не список хвостов.


**Чего здесь нет — и это измерено, а не умолчано:**

- **Оценки качества извлечения нет.** Эталон размечен моделью, а не человеком,
  поэтому метрики годятся как проверка пайплайна и не годятся как оценка
  качества: ошибки разметчика коррелируют с ошибками измеряемой системы
  ([ADR-026](DECISIONS.md)).
- **Агент не доведён до «решает задачи».** 20% завершённых циклов — предел
  `qwen2.5:3b` в удержании состояния между шагами. Облачных прогонов
  в проекте нет по решению владельца ([ADR-034](DECISIONS.md)).
- **На 15% вопросов вне домена система отвечает вместо отказа.** Дефект
  измерен и осознанно не чинится: починка требует классификатора домена
  со своим эталоном ([ADR-032](DECISIONS.md)).

Числа, которые выглядят плохо, опубликованы как есть — в двух местах
локальная LLM проиграла простому базлайну, и это в проекте написано прямо.
Что доказано каждым майлстоуном — в таблице [«Майлстоуны»](#майлстоуны),
почему принято каждое решение — в [DECISIONS.md](DECISIONS.md) (34 записи),
как проект защищается словами — в [PITCH.md](PITCH.md).

## Чем это не дублирует Open Food Facts

У Open Food Facts есть собственный парсер состава на основе таксономии: поля
`ingredients_tags`, `additives_tags`, `allergens_tags`. На грязном многоязычном
тексте с опечатками и вложенными скобками он проваливается, и база сама это
признаёт полем `unknown_ingredients_n`.

Отсюда три вещи, которых в базе нет:

1. **Число разных форм сахара в составе.** Сироп глюкозы, мальтодекстрин,
   декстроза, фруктоза, инвертный сироп — разные названия одного смысла.
   OFF считает добавки, но эту величину не считает вообще.
2. **Разбор там, где таксономия не справилась.** Корпус для LLM отбирается со
   смещением в `unknown_ingredients_n > 0` — ровно туда, где парсер OFF
   бессилен. Это измеримый ответ на вопрос «зачем здесь LLM».
3. **Оценка качества по одному тексту состава**, без таблицы питательности —
   у многих продуктов её просто нет.

Парсер OFF при этом становится бесплатным rule-based baseline: в оценке качества
сравниваются три системы, а не две.

## Стек

Python 3.12 (uv) · DuckDB · PostgreSQL 16 + pgvector · SQLAlchemy 2.x async +
Alembic · Pydantic v2 · FastAPI + uvicorn · Ollama (`qwen2.5:3b-instruct-q4_K_M`,
генерация по JSON-схеме) · `bge-m3` для мультиязычных эмбеддингов ·
aiogram 3 · MCP Python SDK · `zxing-cpp` для чтения штрихкода с фото ·
Langfuse · Docker Compose · GitHub Actions

Всё работает на локальной модели: 6 ГБ VRAM, 3B в q4. Адаптер облачного
провайдера (Anthropic) написан и покрыт тестами через замоканный транспорт —
он показывает, что смена провайдера это строка в `.env`, — но облачных
прогонов в проекте нет: [ADR-034](DECISIONS.md).

Агентных фреймворков нет намеренно: LangChain, LlamaIndex и подобные
в проект не взяты, агент написан руками и умещается в один файл. Это часть
демонстрации, а не экономия.

## Быстрый старт

Нужны Docker, [uv](https://docs.astral.sh/uv/) и [Ollama](https://ollama.com/)
с моделями `qwen2.5:3b-instruct-q4_K_M` и `bge-m3`. Без Ollama работают
загрузка данных и карточка продукта по штрихкоду; поиск, RAG и агент — нет.

```bash
git clone <репозиторий>
cd nutri-radar

cp .env.example .env
# Проверьте DB__PORT: если на машине уже стоит PostgreSQL службой или запущены
# контейнеры других проектов, порт 5432 будет занят. Симптом неочевиден —
# подключение молча уходит в чужую базу.

docker compose up -d db
uv sync
uv run alembic upgrade head
uv run nutri-radar health
```

`health` выводит пять проверок. Отсутствие ключа Anthropic — это `WARN`,
а не ошибка, и это **штатное состояние проекта**: он целиком работает
на локальной модели, а облачных прогонов в нём нет по решению владельца
([ADR-034](DECISIONS.md)).

```
[OK  ] Postgres: соединение         PostgreSQL 16.14
[OK  ] Postgres: расширение vector  версия 0.8.5
[OK  ] Alembic: ревизия             0001 (head)
[OK  ] Ollama: модели               обе модели на месте
[WARN] Anthropic: ключ              не задан — облачная модель недоступна
```

### Загрузка данных

```bash
uv run nutri-radar ingest probe          # разведать схему дампа, не скачивая его
uv run nutri-radar ingest dump           # скачать дамп (7,7 ГБ), идемпотентно
uv run nutri-radar ingest probe --local  # то же на скачанном файле, в разы быстрее
uv run nutri-radar ingest select --stats --dry-run   # статистика выборки без записи
uv run nutri-radar ingest select         # залить корпус в Postgres
uv run nutri-radar ingest delta          # применить инкрементальные обновления
```

### Извлечение структуры состава

```bash
uv run nutri-radar extract corpus                 # состав LLM-корпуса, без записи
uv run nutri-radar extract benchmark              # замер трёх промптов, отчёты в reports/
uv run nutri-radar extract run --prompt v3        # полный прогон, возобновляемый
uv run nutri-radar extract dict sync              # словарь алиасов из data/dictionaries/ в БД
uv run nutri-radar extract dict unknown --top 50  # куда пополнять словарь — по данным
```

Замер обязателен до полного прогона: он показывает секунды на продукт, токены и
экстраполяцию, и предупреждает, если оценка превышает `EXTRACT__MAX_RUN_HOURS`.
Прогон возобновляемый — Ctrl+C стоит не больше одного батча, повторный запуск
продолжает с необработанных продуктов и дублей не создаёт.

`ingest probe` отвечает на вопросы, которые нельзя решить по документации:
официальный `data-fields.txt` описывает CSV-экспорт, а у Parquet другая схема
с вложенными структурами. Работает по сети, до скачивания дампа.

### Витрина: API, бот, MCP

```bash
uv run nutri-radar serve api             # HTTP-API -> http://localhost:8000/docs
uv run nutri-radar serve bot             # Telegram-бот, нужен BOT__TOKEN
uv run nutri-radar serve mcp             # MCP-сервер на stdio
```

В контейнере API входит в базовый стек, бот — в отдельный профиль:

```bash
docker compose up -d api                 # поднимет и базу
curl -s localhost:8000/healthz

docker compose --profile bot up -d bot   # только если задан BOT__TOKEN
```

Бот вынесен в профиль намеренно: без токена он не стартует, а падающий
сервис ронял бы весь `docker compose up`. MCP-сервер сервисом не оформлен —
он общается по stdio, и запускает его клиент (Claude Desktop, IDE),
а не compose.

### Разработка

```bash
uv run pytest                  # юнит-тесты, докер не нужен
uv run pytest -m integration   # требует поднятой БД
uv run ruff check .            # линт
uv run mypy src                # типы
```

Трассировка через Langfuse подключается отдельным профилем на M6:

### Извлечение структуры состава: выбор промпта (M2)

Три версии промпта на одной и той же выборке из 20 продуктов, по 4 на каждый
из пяти языков. Модель `qwen2.5:3b-instruct-q4_K_M`, локально.

| | v1 минимальный | v2 подробные правила | **v3 выбрана** |
|---|---|---|---|
| Форм сахара в среднем | 0,40 | 0,55 | **1,26** |
| Составов без единой формы сахара | 75% | 55% | 53% |
| Ингредиентов извлечено | 8,2 | 7,5 | 10,3 |
| Медиана, с/продукт | 5,61 | 11,09 | 14,20 |
| Невалидных ответов | 0 | 0 | 0 |

Ноль невалидных ответов из 60 вызовов — результат генерации по JSON-схеме
через параметр `format`, а не просьбы соблюдать формат в тексте промпта.

Что важно знать об этих числах:

- **Строка «медиана» здесь недействительна.** Замер снимался с перегретого
  GPU: через два часа машина ушла в тепловую защиту. Повтор того же замера
  на остывшей машине дал 4,27 с вместо 14,20 при тех же токенах — разница
  в 3,3 раза. Числа качества это не задевает, они от скорости не зависят.
  Разбор — ADR-020.
- **53% составов остаются без единой найденной формы сахара** даже на лучшей
  версии промпта. Корпус — снеки, кондитерка и сладкие напитки, так что это
  предел системы, а не свойство продуктов. Чей именно это предел, **M3 выяснить
  не удалось**: эталон размечен моделью, а не человеком, и на такой линейке
  обе гипотезы дают одинаковую картину (ADR-026).
- **Разброс между идентичными прогонами — 20%** (те же продукты, тот же промпт,
  `temperature=0`). Разницу меньше 20% по одному прогону считать значимой
  нельзя.
- **Параллелизм запросов не ускоряет прогон** на 6 ГБ VRAM: A/B на одних
  продуктах дал 838 с при параллелизме 2 и 817 с при 1. Подробности — ADR-017.
- Корпус сужен с 3000 до 1200 продуктов по факту замера. Решение принималось
  по завышенной вдвое оценке времени (см. выше); корпус оставлен прежним,
  чтобы не смешивать в одной выборке данные, снятые при разных условиях.

По языкам форм сахара находится неравномерно: de 2,42 · pl 1,98 · fr 1,93 ·

### Извлечение структуры состава (M3)

> **Эти числа не являются оценкой качества извлечения.** Эталон, на котором
> они посчитаны, размечен не человеком, а моделью `claude-opus-5` — правило 6
> брифа нарушено осознанно, по решению владельца проекта. Читать таблицу
> как «одна система лучше другой» нельзя; почему — сразу под ней.

| Система | F1 ингредиентов | F1 типов | Точность числа форм сахара | Токены | Стоимость полного прогона |
|---|---|---|---|---|---|
| Парсер OFF (rule-based) | 0,397 | 0,222 | 0,375 | 0 | 0 |
| `qwen2.5:3b` локально | 0,295 | 0,114 | 0,600 | 21 870 | 0 (своё железо) |
| Claude (облако) | не прогонялась | — | — | — | — |

Эталон: **40 продуктов** (ru 20, de 20) из запланированных 100. Полный
отчёт — `reports/evals_m3_model_annotated.md`, воспроизводится командой
`nutri-radar evals report`.

**Почему облачных моделей нет в таблице.** Механика прогона собрана целиком
и покрыта тестами через замоканный транспорт, но `ANTHROPIC__API_KEY`
в проекте нет и не будет: владелец решил остаться на локальной модели
([ADR-034](DECISIONS.md)). Изначальное обоснование — ADR-024.

**Почему числам нельзя верить как оценке качества.** Разметчик — языковая
модель, и одна из оцениваемых систем тоже языковая модель. Ошибаются они
на пересекающихся местах: где `qwen2.5:3b` пропустил нестандартную форму
сахара, размечавшая модель с заметной вероятностью пропустила её же. Ошибки
коррелированы, поэтому F1 завышен, а перекос между языками занижен. Разбор —
ADR-026.

**Что из таблицы верно независимо от разметчика.** Парсер OFF показывает
0,00 форм сахара на всех сорока продуктах — не потому что плохо ищет, а потому
что не классифицирует вовсе: таксономия OFF отдаёт `ingredients_tags` без
типов, всё попадает в `base`, кроме E-номеров. Числа разных форм сахара —
той величины, которой в OFF нет и ради которой затевался M2, — он не даёт
в принципе. Это свойство системы, и оно останется верным на любом эталоне.

**Что даёт гейт в CI.** Он сравнивает метрики с зафиксированным базлайном
и падает при просадке больше 3 пунктов F1. Линейке для этого не обязательно
быть человеческой — обязательно быть неподвижной, поэтому регрессии кода
гейт ловит и на таком эталоне. Базлайн хранит отпечаток эталона: подмена
набора даёт отдельную ошибку «эталон изменился», а не ложную просадку
(ADR-025).

**Как вернуть майлстоуну силу:** переразметить эталон руками —
`rm data/evals/extraction_gold.jsonl` и
`nutri-radar evals annotate --annotator "<имя>" --lang ru`. Инструмент
разметки готов и слеп к предсказаниям модели по умолчанию.

### Оценка качества по тексту состава (M4)

Задача: предсказать `nutriscore_grade` продукта, видя **только текст состава**.
Ни одного нутриента в признаках — Nutri-Score считается по ним, и подмешать их
значило бы заново вывести формулу вместо предсказания по составу. Защита
структурная: выгрузка из базы физически не берёт эти колонки.

Все четыре подхода померены на **одной подвыборке в 1000 продуктов**,
воспроизводимой по seed. Полный тест (26 388 продуктов) есть в отчёте, но
сравнивать между собой можно только числа с общей подвыборки: бриф запрещает
гонять через LLM больше нескольких тысяч продуктов, и таблица «TF-IDF
на 26 тысячах против LLM на тысяче» сравнивала бы две разные задачи.

| Подход | Accuracy | Обгон базлайна | macro-F1 | Обучение | Инференс, с/1000 |
|---|---|---|---|---|---|
| **TF-IDF + логрегрессия** (train 105k) | **68,4%** | **+24,1** | 0,595 | 769 с | **1,5** |
| TF-IDF + логрегрессия (train 25k) | 67,9% | +23,6 | 0,600 | 105 с | 1,5 |
| Эмбеддинги `bge-m3` + логрегрессия | 61,6% | +17,3 | 0,504 | 23 мин GPU | 50,8 |
| `qwen2.5:3b` zero-shot, промпт `grade_v2` | 30,6% | **−13,7** | 0,204 | 0 | 532,5 |
| `qwen2.5:3b` zero-shot, промпт `grade_v1` | 28,5% | **−15,8** | 0,135 | 0 | 601,3 |

Базлайн «всегда самый частый класс» (`e`) — **44,3%**. Без него accuracy
нечитаема: 45% выглядит работающей моделью ровно до тех пор, пока не выяснится,
что вырожденная строчка `return "e"` даёт 44,3%.

**Результат оказался сильнее ожидания.** Бриф предполагал, что TF-IDF будет
«почти так же хорош, как LLM, но в сотни раз дешевле». На деле TF-IDF **на 40
пунктов точнее** локальной LLM и в 400 раз дешевле по времени инференса.
Локальная `qwen2.5:3b` не просто проигрывает — она работает **хуже одной
строчки «всегда e»**: ответила «d» на 872 продуктах из 1000 при нуле отказов.
Модель уверенно выдаёт средний класс, не различая составы.

**Эмбеддинги тоже проиграли символьным n-граммам** — 61,6% против 67,9%
на том же обучающем наборе, при 34-кратной стоимости инференса. Список
ингредиентов ближе к мешку технических терминов, чем к связному тексту:
точное совпадение подстрок (`gluco`, `lecith`, `-ose`) работает здесь лучше
семантической близости, ради которой эмбеддинги и берут.

**Почему в таблице две строки TF-IDF.** Полный корпус эмбеддингам не по
карману: замер дал 0,099 с на продукт, то есть 219 минут GPU. Train для них
урезан до 25 тысяч, и без контрольного прогона TF-IDF на тех же 25 тысячах
разницу подходов было бы не отличить от разницы в размере выборки. Размер
стоит 3 пункта, разница подходов — 6.

**Модель учит состав, а не язык.** Корпус смещён по странам (fr 48%, ru 0,2%),
и модель могла бы выучить «текст по-французски → скорее d». Проверка сделана
до сравнения: внутри каждого языка, где язык предиктором быть не может, модель
обгоняет свой внутриязыковой базлайн на **+25,5 (de), +21,7 (fr), +15,0 (en)**
пункта. Отчёт — `reports/m4_nutriscore_grade_sanity.md`.

**Дело не в промпте.** Одна формулировка — слабое основание для такого
утверждения, поэтому промптов два. `grade_v2` даёт рубрику по каждому классу:
как выглядит состав продукта категории `a`, `c`, `e`. Прибавка — 2,1 пункта,
доля ответов `d` упала с 87% до 80%, вывод не сдвинулся. Вторая задача (NOVA)
с другим набором классов и другим промптом дала то же самое.

**Границы утверждения.** Это результат про **локальную 3B-модель в q4 на 6 ГБ
VRAM**, а не про языковые модели вообще. Облачная здесь не проверялась
и не будет: проект остаётся на локальной модели (ADR-024, ADR-034).
Правдоподобно, что модель уровня Sonnet справилась бы заметно лучше — но она
и стоила бы денег за каждый из 131 939 продуктов, тогда как логрегрессия
обучается за 13 минут CPU один раз и дальше стоит 1,5 секунды на тысячу.
Именно этот расчёт, а не абсолютная точность, и есть ответ на вопрос
«что брать». Разбор — ADR-028.

Полные таблицы, разбивка по языкам и матрицы ошибок — в отчёте, который
пересобирается из закоммиченных метрик одной командой:

```bash
uv run nutri-radar analytics report --target nutriscore_grade
```

### Степень переработки по тексту состава (M4)

Вторая задача майлстоуна: предсказать `nova_group` — группу переработки
по классификации NOVA. Та же машинерия, тот же сплит, та же общая подвыборка.

| Подход | Accuracy | Обгон базлайна | macro-F1 | Обучение | Инференс, с/1000 |
|---|---|---|---|---|---|
| **TF-IDF + логрегрессия** (train 110k) | **94,1%** | **+18,4** | 0,844 | 272 с | **1,0** |
| TF-IDF + логрегрессия (train 25k) | 91,6% | +15,9 | 0,806 | 35 с | 1,2 |
| Эмбеддинги `bge-m3` + логрегрессия | 89,8% | +14,1 | 0,774 | 17 мин GPU | 43,4 |
| `qwen2.5:3b` zero-shot | 72,8% | **−2,9** | 0,542 | 0 | 1015,1 |

Базлайн большинства класса (`4` — ультрапереработанные) — **75,7%**.

**Порядок подходов тот же, и LLM снова под базлайном** — на другой задаче,
другом промпте и другом наборе классов. Это уже не случайность одной
формулировки.

**NOVA предсказывается заметно лучше Nutri-Score** — 94,1% против 68,4%,
и это ожидаемо. Степень переработки видна в составе прямо: длинный список
с эмульгаторами, модифицированными крахмалами и ароматизаторами и есть
определение группы 4. Nutri-Score же считается по нутриентам, которых
в тексте нет вовсе, и модель восстанавливает их по косвенным признакам.

**Класс `2` исключён из задачи.** Он встречается 25 раз на 138 254 продукта:
модель на нём ничему не научится, а macro-F1 усреднился бы по величине,
про которую нельзя сказать ничего. Объединять его с классом `1` неверно
по существу — NOVA 1 это необработанная еда, NOVA 2 кулинарные ингредиенты
(масло, соль, сахар), которые не едят сами по себе. Решение принято до
прогона и записано в ADR-027.

Проверка на языковое смещение пройдена и здесь: внутри языков обгон
внутриязыкового базлайна составляет **+19,1 (de), +17,1 (fr), +11,6 (en)**
пункта — `reports/m4_nova_group_sanity.md`.

### Поиск и RAG (M5)

Профиль продукта (название, бренд, категории, состав) векторизуется `bge-m3`
и лежит в pgvector: **146 350 векторов, 414 МБ**, индекс HNSW на `halfvec(1024)`
— 381 МБ, собирается за 48 секунд.

| Метрика | Значение |
|---|---|
| Доля выдачи с запрошенным свойством (top-5) | **47,0%** |
| Медианная латентность поиска | **34 мс** |
| Доля ссылок RAG, ведущих в выдачу | 84,2% |
| Выдуманных штрихкодов | 1 на 20 ответов |

**Почему не recall@5.** Так планировалось, и так не получилось — первая версия
оценки дала 0,0% на всех двадцати запросах. Причина была не в поиске: под
условие «шоколад с пальмовым маслом» подходят **2035 продуктов**, под «снеки
с глутаматом» — 1952, и требовать, чтобы в первой пятёрке оказались именно те
три, что оракул выбрал случайно из двух тысяч, — задача с нулевым решением
у любого поиска, включая идеальный. Число измеряло ошибку в методике.

При тысячах верных ответов правильный вопрос другой: **обладают ли найденные
продукты запрошенным свойством.** Он проверяется тем же точным условием,
которым определялся эталонный набор, и отвечает буквально на то, что спросил
пользователь. Разбор — ADR-029.

**Где поиск работает и где нет** — разброс большой и объяснимый:

| Запрос | Из 5 |
|---|---|
| чипсы с паприкой · `Schokolade mit Haselnüssen` · `sweets with carnauba wax` · `yaourt aux fruits` | **5** |
| `cheese made from pasteurised cow milk` | 4 |
| шоколад с пальмовым маслом · снеки с глутаматом натрия | 2 |
| `chocolate without palm oil` · напитки с аспартамом | 1 |
| продукты с инулином · продукты с диоксидом титана · хлопья с сушёными ягодами | **0** |

Закономерность видна: **ингредиент вместе с категорией** находится почти
идеально, и сразу на трёх языках. **Ингредиент без категории** проваливается —
одно слово размывается среди тридцати других в профиле, и близость набирают
продукты, похожие «в целом».

**Отрицание не работает.** `chocolate without palm oil` даёт 1 из 5: модель
ловит «chocolate» и «palm oil», а «without» для неё почти ничего не значит.
Известное свойство плотных эмбеддингов — здесь оно измерено, а не предположено.
Лечится фильтром в SQL, а не эмбеддингом: поиск умеет `--lang`, `--grade`
и другие точные условия ровно для таких случаев.

**RAG отвечает только по найденному.** Отказ «не знаю» формируется **кодом**,
а не просьбой в промпте: при пустой или далёкой выдаче модель не вызывается
вовсе. Проверено на живом корпусе — запрос «как починить двигатель внутреннего
сгорания» находит энергетики с близостью 0,38, порог 0,5 их отсекает,
и система честно отказывается вместо правдоподобного текста.

Ссылки на штрихкоды обязательны, и подтверждённость считается **кодом, а не
моделью**: штрихкод либо был в выдаче, либо нет. Попросить модель оценить
собственный ответ значило бы измерить её самооценку.

**Оговорка про эталон.** 20 запросов составил ассистент, хотя правило 6 брифа
отдаёт это человеку. Смягчение: эталон **не зависит от оцениваемой системы** —
формулировки написаны словами, а список верных ответов выводит точное условие
SQL, а не просмотр выдачи поиска. Провенанс `author: sql-oracle` в каждой
записи. Ограничение метода: оракул умеет только то, что выражается совпадением
подстроки, и запросов вроде «что-нибудь лёгкое на завтрак» в наборе нет —
а именно они интереснее всего для семантического поиска.

Отчёт пересобирается одной командой:

```bash
uv run nutri-radar retrieval evaluate
```

### Агент с инструментами (M6)

Агент написан руками: без LangChain, LlamaIndex и аналогов. Цикл «план →
инструмент → наблюдение → ответ» умещается в один файл `agent/loop.py`
и объясняется построчно — это и есть предмет демонстрации, а не деталь
реализации.

Три инструмента: `vector_search` (поиск M5), `sql_query` (SELECT по базе),
`lookup_barcode` — **единственное место, где проект ходит в живой API Open
Food Facts**, по одному штрихкоду за вызов.

**Прогон на 10 вопросах, модель `qwen2.5:3b-instruct-q4_K_M`:**

| Величина | Значение |
|---|---|
| Выбрал ожидаемый инструмент первым вызовом | **100%** (10 из 10) |
| Дошёл до ответа | **20%** |
| Ответов со ссылками на штрихкоды | 50% |
| Повторных вызовов всего | **14** |
| Шагов в среднем | 4,4 |
| Токенов в среднем | 7 650 |

**Результат разделяется надвое, и это главное наблюдение майлстоуна.**

**Выбор инструмента работает безупречно.** Вопрос про штрихкод ведёт
в `lookup_barcode`, вопрос про подсчёт — в `sql_query`, вопрос про состав —
в `vector_search`. Десять из десяти, причём **первым же вызовом**: это
не «позвал где-то среди восьми шагов», а именно верный выбор с первого
раза. Описания инструментов и схема действия свою работу делают.

**Завершение цикла не работает.** Модель не понимает, что уже получила
ответ, и зовёт тот же инструмент ещё 2–5 раз: 14 повторов на 10 вопросов.
До ответа дошло 20%, остальное упёрлось в лимиты или выдало пустой ответ.

Это ровно то, что предсказывал план **до** прогона: M4 измерил ту же
модель на том же корпусе — 28,5% против базлайна 44,3%. Модель, не
справившаяся с выбором из пяти классов, не удерживает состояние диалога
из нескольких шагов. Ограничение не в архитектуре агента, а в модели:
код написан против порта `StructuredLLM`, и смена на облачную модель —
это строка в `.env`, а не переписывание.

**Лимиты сработали как задумано.** Потолок в 8 шагов и 20 000 токенов
остановил зацикливание там, где модель не остановилась сама. Без них
прогон не закончился бы: это условие завершимости, а не настройка удобства.

**Что эти числа не говорят.** Ни одно из них не проверяет, был ли ответ
**верным**. Проверка верности требует человека (правило 6), и подменять её
автоматикой значило бы получить красивую цифру ни о чём. Измерено только
то, что видно из протокола.

Наблюдаемость — Langfuse в отдельном compose-профиле (шесть контейнеров,
цена архитектуры v3). Без ключей трассировка деградирует до логов,
и агент от этого не падает:

```bash
docker compose --profile tracing up -d
uv run nutri-radar agent evaluate
```

### Витрина (M7)

Три точки входа поверх готовых слоёв. Логики в них нет: разобрать вход,
вызвать слайс, отформатировать ответ.

**HTTP-API (FastAPI).** Пять эндпойнтов: описание сервиса с атрибуцией,
готовность среды, карточка продукта по штрихкоду, семантический поиск,
ответ со ссылками на штрихкоды и прогон агента.

```bash
curl -s localhost:8000/products/4016463697295 | jq '{source, distinct_sugar_forms}'
# {"source": "corpus", "distinct_sugar_forms": 30}

curl -s -X POST localhost:8000/ask -H 'content-type: application/json' \
  -d '{"question": "какие есть конфеты без сахара", "limit": 3}'
```

Замеры сквозного прогона на живых данных: поиск **6,9 с** с холодной
моделью и **0,5 с** с загруженной, полный RAG-ответ — **13,4 с** при нуле
выдуманных штрихкодов.

Коды ответов различают, **чей** отказ: 400 — ввод не похож на штрихкод,
404 — продукта нет нигде, 502 — плохо ответил внешний источник, 503 —
недоступны база или Ollama, 504 — не уложились в таймаут. Свалить всё
в 500 значило бы лишить клиента возможности решить, повторять ли запрос.

**Telegram-бот (aiogram 3).** Штрихкод цифрами, фото штрихкода
(`zxing-cpp`) и свободный вопрос. Карточка живёт одним редактируемым
сообщением с инлайн-кнопками «Состав», «Формы сахара», «Похожие продукты» —
нажатия правят то же сообщение, а не сыплют новыми.

Атрибуция ODbL и дисклеймер о краудсорсинговых данных стоят
**в первом сообщении `/start`**, а не в подвале справки, и это проверяется
тестом по подстроке.

**MCP-сервер.** Три инструмента агента наружу по stdio для любого
MCP-клиента. Имена и описания берутся из того же реестра, что видит агент:
описание инструмента — часть промпта, и две разошедшиеся копии дали бы
разное поведение агента и внешнего клиента.

**Что здесь сделано структурно, а не дисциплиной:**

| Требование | Как обеспечено |
|---|---|
| Две модели не в VRAM одновременно | очередь `llm/runtime.py`; тест смотрит на порядок запросов к Ollama |
| Нет оценочных ярлыков | список основ в `wording.py`, проверка по всем текстам разом |
| Атрибуция в первом сообщении | тест по подстроке на `/start` |
| Данные пользователя не в логах | middleware пишет хэш чата и длину текста, но не текст |
| Фото не ложится на диск | декодирование из байтов в памяти |

### Живой прогон витрины

Бот прогнан в реальном Telegram 11.09.2026. До этого момента в README
стояла честная оговорка «не прогонялся, токена нет»; теперь она снята,
и вот что прогон показал.

**Что подтвердилось.**

| Требование брифа | Как проверено живьём |
|---|---|
| Чтение штрихкода с фото упаковки | `zxing-cpp` — **64 мс** с первой попытки на реальном снимке |
| Атрибуция ODbL и дисклеймер в первом сообщении | пришли первым сообщением `/start`, до любого ответа |
| Карточка показывает скрытые формы сахара | продукт из корпуса — **30 разных форм** |

**Три дефекта, которых не нашли 714 тестов.** Все три исправлены
(коммит `93fa3ca`):

1. **404 от Open Food Facts трактовался как отказ источника.** «Такого
   штрихкода нет» — это ответ, а не поломка: 404 означает, что источник
   работает и продукта в нём нет. Пользователь видел «внешний источник
   недоступен» вместо «продукт не найден».
2. **HTML-разметка показывалась сырой.** 36% корпуса приходит с
   `<span class="allergen">`; в поиске это снимается, в карточке бота —
   не снималось.
3. **Приписка про штрихкоды приходила под ответом без ссылок.**
   «Числа в квадратных скобках — штрихкоды» под ответом, где скобок нет.

**Почему тесты этого не поймали.** Все три — про склейку слоёв, а не про
слой. Каждый компонент вёл себя ровно так, как записано в его тесте:
адаптер OFF честно различал 404 и 502, а бот честно показывал то, что
ему дали. Тесты проверяли то, что автор считал важным; прогон проверил
то, что происходит. Разбор — ADR-031, решение 8.

**Что прогон оставил без чисел — и что эти числа оказались.**

| Величина | Значение | |
|---|---|---|
| Ответов на языке вопроса | **76,5%** | знаменатель 17 из 20 |
| Честных отказов на вопросах вне домена | **15,0%** | из 20 вопросов |
| Цена переключения модели на 6 ГБ VRAM | **9,5 с** | разница медиан 11,5 с |

**Язык ответа: 76,5%.** Правило «отвечай на языке вопроса» в промпте
`rag_v1` есть — пунктом 5. Число измеряет не отсутствие инструкции,
а то, как часто модель на 3B её игнорирует: почти каждый четвёртый ответ.
Язык определяется по алфавиту, кириллица против латиницы; немецкие и
французские запросы этим признаком неразличимы и выведены из знаменателя
целиком, а не записаны в промахи — иначе метрика измеряла бы ограничение
прибора. Первый прогон дал 70,0% ровно по этой ошибке, и она исправлена
до того, как число куда-то пошло.

Попытка починить структурным принуждением (`rag_v2`: поле `language`
первым в JSON-схеме) **провалилась и это опубликовано**: принуждение
сработало, модель начала писать по-русски — и ушла в вырожденный повтор,
дословно повторяя одну фразу до упора в лимит вывода. Отказов на эталоне
стало 70,0% против нуля у `rag_v1`. Версией по умолчанию остаётся
`rag_v1`; `rag_v2` лежит в репозитории как измеренный результат. Таблица
сравнения — ADR-032.

**Отказ вне домена: 15,0%.** «Сколько стоит хлеб» проходит мимо порога
`MIN_SIMILARITY`: хлеб в базе есть, близость высокая, просто вопрос
не про состав. На 20 посторонних вопросах — цена, доставка, рецепты,
погода, личные советы по питанию — система отказала в трёх случаях.
По рецептам, доставке и личным советам по питанию — **ни одного отказа**,
а это прямо за границами продукта из брифа. Дефект измерен и не исправлен:
починка требует либо подбора порога под пример, либо классификатора
домена со своим эталоном — и то и другое вынесено за границы этой работы
осознанно (ADR-032).

**Цена переключения моделей: 9,5 с.** В живом прогоне два вопроса подряд
заняли 15,6 с и 88 с. Замер подтвердил причину: одни и те же вопросы
подряд на одной модели дают медиану 2,5 с, с чередованием — 14,0 с.
Разница и есть цена загрузки весов, когда `qwen2.5:3b` и `bge-m3`
не помещаются в видеопамять вдвоём. Бот живёт во второй строке: он
получает вопросы по одному. Это замер, а не оптимизация — число
публикуется как ограничение железа.

```bash
uv run nutri-radar retrieval evaluate          # язык и отказ вне домена
uv run nutri-radar retrieval switch-benchmark  # цена переключения
```

**Оговорка про перемер.** Подтверждённость в таблице M5 выше — 84,2%,
на перемере того же `rag_v1` вышло 88,8%. Версия промпта не менялась,
менялся только прогон: локальная модель даёт разброс между идентичными
запусками, и его величина измерена отдельно (ADR-018). Старое число
не подменено новым — оба относятся к `rag_v1` и оба верны для своего
прогона.

## Источник данных и атрибуция

Данные о продуктах взяты из **[Open Food Facts](https://world.openfoodfacts.org/)** —
открытой краудсорсинговой базы пищевых продуктов.

База данных Open Food Facts доступна по лицензии
**[Open Database License (ODbL) v1.0](https://opendatacommons.org/licenses/odbl/1-0/)**.
Отдельные её содержимые элементы распространяются по лицензии
**[Database Contents License (DbCL) v1.0](https://opendatacommons.org/licenses/dbcl/1-0/)**.

Использование данных в этом проекте не подразумевает одобрения со стороны
Open Food Facts или его участников.

Массовые данные берутся **дампом**, а не через живой API: разработчики Open Food
Facts прямо просят не выкачивать базу через API. Живой API используется только
для точечного запроса по одному штрихкоду, и весь такой доступ собран
в единственном модуле `openfoodfacts.py`. У него два потребителя: инструмент
`lookup_barcode` у агента и карточка продукта, когда штрихкода нет в корпусе
(147 тысяч продуктов из 4,63 млн — большинство реальных сканов туда
не попадает). Подробности — ADR-031.

### Что нужно знать об источнике

- **Parquet-дамп лежит только на HuggingFace.** На `static.openfoodfacts.org`
  его нет — там CSV, JSONL и MongoDB-дамп.
- **Дельта-экспорты не отслеживают удаление продуктов.** Это ограничение самого
  Open Food Facts: инкрементальные обновления приносят изменённые и новые
  записи, но не сообщают об удалённых. Полностью консистентное состояние даёт
  только перезалив полного дампа. Хранение дельт — 14 дней; если последний
  прогон был раньше, часть истории потеряна безвозвратно, и система об этом
  предупредит.
- **Формат дельт отличается от формата дампа.** В дампе состав лежит списком
  структур с полем языка, в дельтах — плоскими ключами `ingredients_text_en`.
  Поэтому источников два, а не один с разными путями.
- **У записей дампа пять разных версий схемы** (`999`, `1001`–`1004`): состав
  заполненных полей различается от записи к записи.
