# Nutri Radar

Разбор состава пищевых продуктов: нормализация грязных многоязычных списков
ингредиентов, поиск скрытых форм сахара и добавок, предсказание оценки качества
питания по одному тексту состава, ответы на вопросы по базе со ссылками на
конкретные штрихкоды.

> **Инструмент прозрачности состава, а не медицинский или диетологический
> советчик.** Система показывает, что написано в составе, и ссылается на данные.
> Она не даёт рекомендаций по питанию, не строит диеты, не считает нормы под
> человека и не персонализируется под заболевания или цели по весу.
>
> Данные краудсорсинговые и могут быть неполными или неверными.

**Статус: M2 — извлечение структуры состава, готов к ревью.** В базе
аналитический корпус на **147 842 продукта**, отобранный из 4,63 млн строк
дампа Open Food Facts, и **1187 разборов состава** локальной моделью по
JSON-схеме — с числом разных форм сахара, которого в Open Food Facts нет.
Работают идемпотентное скачивание, выборка через DuckDB, батчевая заливка,
инкрементальные обновления и возобновляемый прогон извлечения.
290 тестов, из них 26 интеграционных.

## Чем это не дублирует Open Food Facts

У Open Food Facts есть собственный парсер состава на основе таксономии: поля
`ingredients_tags`, `additives_tags`, `allergens_tags`. На грязном многоязычном
тексте с опечатками и вложенными скобками он проваливается, и база сама это
признаёт полем `unknown_ingredients_n`.

Отсюда три вещи, которых в базе нет:

1. **Число разных форм сахара в составе.** Сироп глюкозы, мальтодекстрин,
   декстроза, фруктоза, инвертный сироп — разные названия одного смысла.
   OFF считает добавки, но эту величину не считает вообще.
2. **Разбор там, где таксономия не справилась.** Корпус для LLM отбирается со
   смещением в `unknown_ingredients_n > 0` — ровно туда, где парсер OFF
   бессилен. Это измеримый ответ на вопрос «зачем здесь LLM».
3. **Оценка качества по одному тексту состава**, без таблицы питательности —
   у многих продуктов её просто нет.

Парсер OFF при этом становится бесплатным rule-based baseline: в оценке качества
сравниваются три системы, а не две.

## Стек

Python 3.12 (uv) · DuckDB · PostgreSQL 16 + pgvector · SQLAlchemy 2.x async +
Alembic · Pydantic v2 · FastAPI · Ollama (`qwen2.5:3b-instruct-q4_K_M`,
генерация по JSON-схеме) · Anthropic Claude (агент и эталон в evals) ·
`bge-m3` для мультиязычных эмбеддингов · aiogram 3 · Docker Compose ·
GitHub Actions

Агентных фреймворков нет намеренно: агент пишется руками.

## Быстрый старт

Нужны Docker, [uv](https://docs.astral.sh/uv/) и (для будущих майлстоунов)
[Ollama](https://ollama.com/).

```bash
git clone <репозиторий>
cd nutri-radar

cp .env.example .env
# Проверьте DB__PORT: если на машине уже стоит PostgreSQL службой или запущены
# контейнеры других проектов, порт 5432 будет занят. Симптом неочевиден —
# подключение молча уходит в чужую базу.

docker compose up -d db
uv sync
uv run alembic upgrade head
uv run nutri-radar health
```

`health` выводит пять проверок. Отсутствие Ollama или ключа Anthropic — это
`WARN`, а не ошибка: на M0 они ещё не нужны.

```
[OK  ] Postgres: соединение         PostgreSQL 16.14
[OK  ] Postgres: расширение vector  версия 0.8.5
[OK  ] Alembic: ревизия             0001 (head)
[OK  ] Ollama: модели               обе модели на месте
[WARN] Anthropic: ключ              не задан — понадобится на M3 и M6
```

### Загрузка данных

```bash
uv run nutri-radar ingest probe          # разведать схему дампа, не скачивая его
uv run nutri-radar ingest dump           # скачать дамп (7,7 ГБ), идемпотентно
uv run nutri-radar ingest probe --local  # то же на скачанном файле, в разы быстрее
uv run nutri-radar ingest select --stats --dry-run   # статистика выборки без записи
uv run nutri-radar ingest select         # залить корпус в Postgres
uv run nutri-radar ingest delta          # применить инкрементальные обновления
```

### Извлечение структуры состава

```bash
uv run nutri-radar extract corpus                 # состав LLM-корпуса, без записи
uv run nutri-radar extract benchmark              # замер трёх промптов, отчёты в reports/
uv run nutri-radar extract run --prompt v3        # полный прогон, возобновляемый
uv run nutri-radar extract dict sync              # словарь алиасов из data/dictionaries/ в БД
uv run nutri-radar extract dict unknown --top 50  # куда пополнять словарь — по данным
```

Замер обязателен до полного прогона: он показывает секунды на продукт, токены и
экстраполяцию, и предупреждает, если оценка превышает `EXTRACT__MAX_RUN_HOURS`.
Прогон возобновляемый — Ctrl+C стоит не больше одного батча, повторный запуск
продолжает с необработанных продуктов и дублей не создаёт.

`ingest probe` отвечает на вопросы, которые нельзя решить по документации:
официальный `data-fields.txt` описывает CSV-экспорт, а у Parquet другая схема
с вложенными структурами. Работает по сети, до скачивания дампа.

### Разработка

```bash
uv run pytest                  # юнит-тесты, докер не нужен
uv run pytest -m integration   # требует поднятой БД
uv run ruff check .            # линт
uv run mypy src                # типы
```

Трассировка через Langfuse подключается отдельным профилем на M6:
`docker compose --profile tracing up -d`. В базовый стек она не входит —
это шесть контейнеров и 16 ГиБ по рекомендации вендора.

### Извлечение структуры состава: выбор промпта (M2)

Три версии промпта на одной и той же выборке из 20 продуктов, по 4 на каждый
из пяти языков. Модель `qwen2.5:3b-instruct-q4_K_M`, локально.

| | v1 минимальный | v2 подробные правила | **v3 выбрана** |
|---|---|---|---|
| Форм сахара в среднем | 0,40 | 0,55 | **1,26** |
| Составов без единой формы сахара | 75% | 55% | 53% |
| Ингредиентов извлечено | 8,2 | 7,5 | 10,3 |
| Медиана, с/продукт | 5,61 | 11,09 | 14,20 |
| Невалидных ответов | 0 | 0 | 0 |

Ноль невалидных ответов из 60 вызовов — результат генерации по JSON-схеме
через параметр `format`, а не просьбы соблюдать формат в тексте промпта.

Что важно знать об этих числах:

- **Строка «медиана» здесь недействительна.** Замер снимался с перегретого
  GPU: через два часа машина ушла в тепловую защиту. Повтор того же замера
  на остывшей машине дал 4,27 с вместо 14,20 при тех же токенах — разница
  в 3,3 раза. Числа качества это не задевает, они от скорости не зависят.
  Разбор — ADR-020.
- **53% составов остаются без единой найденной формы сахара** даже на лучшей
  версии промпта. Корпус — снеки, кондитерка и сладкие напитки, так что это
  предел системы, а не свойство продуктов. Чей именно это предел, **M3 выяснить
  не удалось**: эталон размечен моделью, а не человеком, и на такой линейке
  обе гипотезы дают одинаковую картину (ADR-026).
- **Разброс между идентичными прогонами — 20%** (те же продукты, тот же промпт,
  `temperature=0`). Разницу меньше 20% по одному прогону считать значимой
  нельзя.
- **Параллелизм запросов не ускоряет прогон** на 6 ГБ VRAM: A/B на одних
  продуктах дал 838 с при параллелизме 2 и 817 с при 1. Подробности — ADR-017.
- Корпус сужен с 3000 до 1200 продуктов по факту замера. Решение принималось
  по завышенной вдвое оценке времени (см. выше); корпус оставлен прежним,
  чтобы не смешивать в одной выборке данные, снятые при разных условиях.

### Извлечение структуры состава: полный прогон (M2)

Корпус 1200 продуктов, промпт v3, `qwen2.5:3b-instruct-q4_K_M` локально,
параллелизм 1.

| Показатель | Значение |
|---|---|
| Разобрано продуктов | 1187 из 1200 |
| Нечитаемых | 38 (3,1%) |
| Отказов модели | 0 |
| Медиана / p95, с на продукт | 5,32 / 19,11 |
| Токены вход / выход | 314 735 / 353 080 |
| **Форм сахара в среднем** | **1,84** |
| Составов без единой формы сахара | 43,9% |
| Ингредиентов в среднем | 12,0 |
| Стоимость | 0 ₽ — модель локальная |

Причины пропусков различаются в БД колонкой `skip_reason`: 23 состава модель
объявила нечитаемыми сама, у 15 ответ упёрся в лимит вывода. Составов, не
влезших в контекст, не оказалось ни одного.

По языкам форм сахара находится неравномерно: de 2,42 · pl 1,98 · fr 1,93 ·
en 1,64 · **ru 1,28**. Русские составы дают заметно меньше всех. Свойство ли
это самих составов или слабость модели на русском — без эталона не различить,
и это прямая задача M3. Стратификация выборки по языкам сработала: в корпусе
229–259 продуктов на каждый из пяти языков.

Повторный запуск после прогона не вызвал модель ни разу и не создал дублей —
1225 строк на 1225 уникальных кодов. Подробности — ADR-021.

### Извлечение структуры состава (M3)

> **Эти числа не являются оценкой качества извлечения.** Эталон, на котором
> они посчитаны, размечен не человеком, а моделью `claude-opus-5` — правило 6
> брифа нарушено осознанно, по решению владельца проекта. Читать таблицу
> как «одна система лучше другой» нельзя; почему — сразу под ней.

| Система | F1 ингредиентов | F1 типов | Точность числа форм сахара | Токены | Стоимость полного прогона |
|---|---|---|---|---|---|
| Парсер OFF (rule-based) | 0,397 | 0,222 | 0,375 | 0 | 0 |
| `qwen2.5:3b` локально | 0,295 | 0,114 | 0,600 | 21 870 | 0 (своё железо) |
| Claude (облако) | не прогонялась | — | — | — | — |

Эталон: **40 продуктов** (ru 20, de 20) из запланированных 100. Полный
отчёт — `reports/evals_m3_model_annotated.md`, воспроизводится командой
`nutri-radar evals report`.

**Почему облачных моделей нет в таблице.** У проекта нет `ANTHROPIC__API_KEY`,
а закрытые модели Anthropic локально не запускаются. Механика прогона собрана
целиком и покрыта тестами — не хватает ровно ключа. Обоснование — ADR-024.

**Почему числам нельзя верить как оценке качества.** Разметчик — языковая
модель, и одна из оцениваемых систем тоже языковая модель. Ошибаются они
на пересекающихся местах: где `qwen2.5:3b` пропустил нестандартную форму
сахара, размечавшая модель с заметной вероятностью пропустила её же. Ошибки
коррелированы, поэтому F1 завышен, а перекос между языками занижен. Разбор —
ADR-026.

**Что из таблицы верно независимо от разметчика.** Парсер OFF показывает
0,00 форм сахара на всех сорока продуктах — не потому что плохо ищет, а потому
что не классифицирует вовсе: таксономия OFF отдаёт `ingredients_tags` без
типов, всё попадает в `base`, кроме E-номеров. Числа разных форм сахара —
той величины, которой в OFF нет и ради которой затевался M2, — он не даёт
в принципе. Это свойство системы, и оно останется верным на любом эталоне.

**Что даёт гейт в CI.** Он сравнивает метрики с зафиксированным базлайном
и падает при просадке больше 3 пунктов F1. Линейке для этого не обязательно
быть человеческой — обязательно быть неподвижной, поэтому регрессии кода
гейт ловит и на таком эталоне. Базлайн хранит отпечаток эталона: подмена
набора даёт отдельную ошибку «эталон изменился», а не ложную просадку
(ADR-025).

**Как вернуть майлстоуну силу:** переразметить эталон руками —
`rm data/evals/extraction_gold.jsonl` и
`nutri-radar evals annotate --annotator "<имя>" --lang ru`. Инструмент
разметки готов и слеп к предсказаниям модели по умолчанию.

## Источник данных и атрибуция

Данные о продуктах взяты из **[Open Food Facts](https://world.openfoodfacts.org/)** —
открытой краудсорсинговой базы пищевых продуктов.

База данных Open Food Facts доступна по лицензии
**[Open Database License (ODbL) v1.0](https://opendatacommons.org/licenses/odbl/1-0/)**.
Отдельные её содержимые элементы распространяются по лицензии
**[Database Contents License (DbCL) v1.0](https://opendatacommons.org/licenses/dbcl/1-0/)**.

Использование данных в этом проекте не подразумевает одобрения со стороны
Open Food Facts или его участников.

Массовые данные берутся **дампом**, а не через живой API: разработчики Open Food
Facts прямо просят не выкачивать базу через API. Живой API используется в одном
месте — точечный поиск по штрихкоду в агенте.

### Что нужно знать об источнике

- **Parquet-дамп лежит только на HuggingFace.** На `static.openfoodfacts.org`
  его нет — там CSV, JSONL и MongoDB-дамп.
- **Дельта-экспорты не отслеживают удаление продуктов.** Это ограничение самого
  Open Food Facts: инкрементальные обновления приносят изменённые и новые
  записи, но не сообщают об удалённых. Полностью консистентное состояние даёт
  только перезалив полного дампа. Хранение дельт — 14 дней; если последний
  прогон был раньше, часть истории потеряна безвозвратно, и система об этом
  предупредит.
- **Формат дельт отличается от формата дампа.** В дампе состав лежит списком
  структур с полем языка, в дельтах — плоскими ключами `ingredients_text_en`.
  Поэтому источников два, а не один с разными путями.
- **У записей дампа пять разных версий схемы** (`999`, `1001`–`1004`): состав
  заполненных полей различается от записи к записи.
