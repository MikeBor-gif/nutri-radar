## 2. Что строим

Система разбирает состав пищевых продуктов: нормализует грязные многоязычные
списки ингредиентов, находит скрытые сахара и добавки, предсказывает оценку
качества по одному тексту состава, отвечает на вопросы по базе со ссылками на
конкретные продукты и разбирает мою корзину.

Слои:

1. **Ingestion** — дамп Open Food Facts → DuckDB → отфильтрованное подмножество в Postgres.
2. **Extraction** — LLM превращает `ingredients_text` в структуру + evals качества.
3. **Analytics** — classic ML на готовых метках из базы.
4. **Retrieval + RAG** — векторный поиск и ответы со ссылками на продукты.
5. **Agent + Serving** — агент с инструментами, FastAPI, Telegram-бот, MCP-сервер.

## 3a. Железо и ограничения

Ноутбук: RTX 3060 Laptop, 6 ГБ VRAM, 64 ГБ RAM.

- Модель для извлечения — 3–4B в 4-битной квантизации. 7B+ не берём.
- Размер контекста задаём **явно**: дефолт Ollama маленький и молча обрезает вход.
- Свободный JSON от маленькой модели ненадёжен → ограничение генерации по
  JSON-схеме, а не просьбы в промпте.
- Составы короткие (обычно до 100 слов), поэтому прогон быстрый. Но:
  **не прогоняем через LLM всю базу.** См. раздел 6 про размер корпуса.
- Эмбеддинги считаем локально, модель обязательно мультиязычная — составы на
  десятках языков.
- Агент работает на облачной модели.
- Прогоны возобновляемые: прогресс в БД, перезапуск продолжает с необработанных.
- Перед полным прогоном — замер на 20 продуктах: секунды на продукт, токены,
  оценка общего времени. В отчёт.

## 4. Правила работы (важнее, чем код)

1. **Один вертикальный слайс за раз.** Сначала «один продукт проходит путь от
   дампа до строки в БД», потом расширяем.
2. **Останавливайся после каждого milestone** и жди моего ревью.
3. **Объясняй решения.** Альтернативы и причины выбора — в `DECISIONS.md`
   (контекст → решение → альтернативы → последствия).
4. **Тесты обязательны** для парсинга, нормализации, извлечения. Внешние вызовы
   мокаются. Тест, ходящий в сеть, — плохой тест.
5. **Никаких магических констант.** Всё в конфиг через pydantic-settings и `.env`,
   в репозиторий только `.env.example`.
6. **Не генерируй эталонную разметку для evals.** Её делаю я руками. Твоя задача —
   инструмент разметки и подсчёт метрик, но не метки.
7. **Не добавляй зависимости** без согласования. LangChain и подобных нет.
8. **Коммит на каждый логический шаг**, conventional commits.
9. **Неоднозначное требование — спроси**, не додумывай молча.
10. **Секреты не попадают в код, логи и коммиты.**

## 6. Источник данных: Open Food Facts

Лицензия ODbL — **атрибуция обязательна**, указать в README и в боте.
Ключ и регистрация не нужны.

**Стратегия сбора (важно, не отклоняйся):**

- У API есть лимиты, и разработчики прямо просят не выкачивать базу через него.
  Поэтому массовые данные берём **дампом**, а API используем только для
  точечного поиска по штрихкоду в агенте.
- Берём **Parquet-версию** дампа (упрощённая, без отладочных колонок), читаем
  через DuckDB — колоночный формат позволяет брать только нужные поля и не
  разворачивать десятки гигабайт.
- Описание полей — в официальном `data-fields.txt`. Прочитай его прежде, чем
  проектировать схему; не угадывай названия колонок.
- Инкрементальное обновление — через дельта-экспорты за последние 14 дней.
- Дамп кладём в `data/`, он в gitignore. Скрипт скачивания идемпотентный.

**Фильтрация корпуса — обязательный этап в DuckDB, до Postgres:**

- Только продукты с непустым текстом состава.
- Языки: `[ЗАПОЛНИТЬ: например en, ru, de, fr, pl]`
- Категории: `[ЗАПОЛНИТЬ: например снеки, молочное, напитки, завтраки — или все]`
- Целевые размеры (уточним по факту):
  - **Аналитический корпус** для classic ML: 50–150 тысяч продуктов. Метки берём
    из базы, LLM не нужна, всё считается на CPU за минуты.
  - **LLM-корпус** для извлечения структуры: 3–5 тысяч продуктов, случайная
    выборка со стратификацией по категориям и оценкам. Больше не надо: локальная
    модель будет молотить сутки, а выводы не изменятся.
- Решение о размерах и обоснование — в `DECISIONS.md`.

## 7. Схема данных (стартовая)

- `products_raw` — штрихкод (PK), исходный JSON выбранных полей, `imported_at`,
  версия дампа. Сырое не перезаписываем деструктивно.
- `products` — нормализованное: название, бренд, категории, страны, языки,
  БЖУ/соль/сахар на 100 г, оценка качества питания, группа переработки,
  флаги наличия данных.
- `product_extraction` — результат LLM: нормализованный список ингредиентов,
  тип каждого (основа / сахар / жир / добавка / ароматизатор / консервант /
  подсластитель), число разных форм сахара, число добавок с E-номером,
  найденные аллергены, доверие модели + `model_name`, `prompt_version`,
  токены, время, `extracted_at`. Версионируется: у продукта может быть несколько
  извлечений разными версиями промпта.
- `ingredients_dict` — канонические ингредиенты и их алиасы по языкам.
- `product_embeddings` — вектор, `model_name`, hnsw-индекс.
- `runs` — журнал прогонов ingestion, extraction, evals.

## 8. Что извлекает LLM (это ядро проекта)

Вход — `ingredients_text`: грязный, многоязычный, с вложенными скобками,
опечатками, процентами, пометками аллергенов вперемешку с самим составом.
Регуляркой это не решается — вот почему здесь нужна модель.

Выход по JSON-схеме:

- нормализованный список ингредиентов в каноническом виде;
- тип каждого ингредиента (см. перечисление в `product_extraction`);
- **сколько разных названий сахара** встречается в составе (сироп глюкозы,
  мальтодекстрин, декстроза, фруктоза, инвертный сироп и прочие) — это ключевая
  производная фича проекта и самая наглядная часть демо;
- количество добавок с E-номером;
- аллергены;
- флаг «состав нечитаем / обрезан», чтобы такие записи не портили аналитику.

Промпт версионируется. Версия пишется в БД рядом с результатом.

## 9. Milestones

**M0 — фундамент.** Репозиторий, pyproject, ruff, pytest, compose с
Postgres+pgvector, alembic, конфиг, health-check, CI на линт и тесты.
*DoD:* `docker compose up` поднимает всё, `pytest` и CI зелёные.

**M1 — ingestion.** Идемпотентное скачивание Parquet-дампа, выборка и фильтрация
через DuckDB по критериям раздела 6, заливка в Postgres батчами, инкрементальное
обновление через дельты. CLI: `ingest dump`, `ingest select`, `ingest delta`.
*DoD:* аналитический корпус в базе, повторный запуск не создаёт дублей, есть
тесты фильтрации на маленьком синтетическом Parquet.

**M2 — извлечение.** Pydantic-схема, промпт v1, вызов локальной модели с
ограничением по JSON-схеме, батчинг, учёт времени и токенов, запись в
`product_extraction`. Нормализация ингредиентов через словарь алиасов.
*DoD:* LLM-корпус обработан, время и стоимость залогированы, замер сделан заранее.

**M3 — evals.** CLI для ручной разметки: показывает состав, я ввожу эталонный
разбор, пишется в `data/evals/gold.jsonl`. Раннер считает precision/recall/F1 по
ингредиентам и по типам, accuracy по числу форм сахара, сравнивает версии
промптов и модели, сохраняет отчёт в `reports/`.

Обязательная часть — **локальная модель против облачной** на одном gold-наборе:
F1, секунды на продукт, стоимость полного прогона. Таблица в README.
Если локальная заметно проигрывает — проектируем гибрид: локальная разбирает всё,
неуверенные случаи переизвлекаются облачной, порог подбирается по данным.
*DoD:* размечено ≥50 продуктов (мной), сравнение ≥3 версий промпта и 2 моделей,
результаты и выводы в README.

**M4 — аналитика.** Три задачи на **готовых метках из базы**, без ручной разметки:

- *Sanity-check:* предсказать оценку качества питания по числовым БЖУ. Она
  считается по формуле, поэтому модель обязана дать почти идеальный результат.
  Если не дала — баг в пайплайне. Это проверка, а не достижение, так и опиши.
- *Основная задача:* предсказать оценку качества **только по тексту состава и
  названию**, без числовых полей. Практически осмысленно: у многих продуктов
  таблицы питательности нет. Сравнить три подхода на одних данных и одной
  метрике: TF-IDF + логрегрессия, эмбеддинги + логрегрессия, LLM zero-shot.
  Отчитаться по качеству, времени и стоимости каждого.
- *Вторая задача:* предсказать группу степени переработки по составу.

Плюс отчёт с графиками: распределение числа форм сахара по категориям, топ
добавок, связь длины состава с оценкой, доля продуктов с пропущенными данными и
как пропуски смещают выводы.
*DoD:* воспроизводимый `analytics report`, графики в `reports/`, честная таблица
сравнения трёх подходов и выводы человеческим языком в README.

> Ожидаемый и самый ценный результат: TF-IDF окажется почти так же хорош, как
> LLM, но в сотни раз дешевле. Если так — напиши это в README прямым текстом.
> Умение не тащить LLM туда, где хватает логрегрессии, — главный сигнал проекта.

**M5 — поиск и RAG.** Эмбеддинги «профиля продукта» (название + категории +
нормализованный состав), pgvector-индекс, семантический поиск, гибрид с
фильтрами по категории, оценке, числу добавок.

Поверх — RAG: вопросы вроде «снеки без пальмового масла с хорошей оценкой»,
«в каких продуктах чаще всего встречается такая-то добавка», «чем отличаются
составы дешёвого и дорогого шоколада». Ответ строится только по найденным
продуктам и **обязательно содержит ссылки на конкретные штрихкоды**. Не нашлось
релевантного — система говорит «не знаю», а не выдумывает.

Метрики: recall@5 на 20 запросах с эталонами + доля утверждений, подтверждённых
найденными продуктами (проверяю вручную).
*DoD:* поиск и RAG работают, обе метрики измерены и в README.

**M6 — агент.** Инструменты: `sql_query` (только SELECT, whitelist таблиц),
`vector_search`, `lookup_barcode` (единственное место, где дёргаем живой API).
Цикл: план → вызов инструмента → проверка → следующий шаг, с лимитом шагов и
лимитом стоимости. Без фреймворков. Трассировка в Langfuse.

Сценарии: разбери список продуктов из моей корзины; найди замену этому продукту
в той же категории с лучшей оценкой; покажи, где в моей корзине больше всего
скрытых форм сахара.
*DoD:* три сценария воспроизводимо отрабатывают, каждый шаг виден в трассировке.

**M7 — витрина.** FastAPI-эндпоинты, Telegram-бот (отправил штрихкод или фото
штрихкода — получил разбор), MCP-сервер поверх базы. CI дополнительно гоняет
evals и падает, если F1 упал больше чем на 3 пункта от зафиксированного baseline.
*DoD:* всё поднимается одной командой, README оформлен как витрина.

## 10. Метрики, которые проект обязан считать

Все числа берутся из кода, не из головы.

- F1 извлечения ингредиентов и их типов; динамика по версиям промпта.
- F1 локальной модели против облачной на одном gold-наборе.
- Accuracy предсказания оценки по тексту: TF-IDF vs эмбеддинги vs LLM — вместе со
  временем и стоимостью каждого подхода.
- Accuracy группы переработки.
- recall@5 семантического поиска.
- Доля утверждений RAG-ответа, подтверждённых источниками.
- Секунды на продукт локально; время и стоимость полного прогона локально и в облаке.
- Доля продуктов с пропущенными данными и её влияние на выводы.

## 11. Границы продукта (обязательно соблюдать)

- Это **инструмент прозрачности состава, а не медицинский или диетологический
  советчик.** Система показывает, что написано в составе, и ссылается на данные.
  Она не даёт рекомендаций по питанию, не строит диеты, не считает нормы под
  человека и не персонализируется под заболевания и цели по весу.
- Никаких оценочных ярлыков вроде «плохая еда» и «нельзя есть». Формулировки
  нейтральные и описательные: «в составе N разных форм сахара», «оценка по базе — C».
- Данные краудсорсинговые и могут быть неполными или неверными. Дисклеймер об
  этом — в README и в первом сообщении бота, вместе с атрибуцией ODbL.
- Никаких целевых показателей калорий, дефицитов и трекинга съеденного.

## 12. Чего не делать

- Не выкачивать базу через живой API — только дамп.
- Не тащить LangChain/LlamaIndex/CrewAI.
- Не заливать весь дамп в Postgres — только отфильтрованное подмножество.
- Не прогонять через LLM больше нескольких тысяч продуктов.
- Не делать веб-фронтенд.
- Не дообучать модели.
- Не хранить пользовательские данные из бота дольше, чем нужно для ответа.
