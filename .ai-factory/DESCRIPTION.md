# Nutri Radar

## Обзор

Система разбирает состав пищевых продуктов: нормализует грязные многоязычные
списки ингредиентов, находит скрытые формы сахара и добавки, предсказывает оценку
качества питания по одному тексту состава, отвечает на вопросы по базе со ссылками
на конкретные штрихкоды и разбирает состав корзины покупок.

Источник данных — Open Food Facts (ODbL, атрибуция обязательна).

**Назначение проекта:** портфолио ML/LLM-инженера. Из этого следует, что
измеримость и защищаемость решений важнее объёма функциональности. Каждое
архитектурное решение фиксируется в `DECISIONS.md` в формате
контекст → решение → альтернативы → последствия, потому что его придётся защищать
словами на собеседовании.

## Ключевая ценность

Проект не дублирует то, что Open Food Facts уже посчитал. У OFF есть собственный
парсер состава на основе таксономии (`ingredients_tags`, `additives_tags`,
`allergens_tags`), и он проваливается на грязном многоязычном тексте — база сама
признаёт это полем `unknown_ingredients_n`.

Отсюда три вещи, которых в базе нет и которые делает Nutri Radar:

1. **Число разных форм сахара в составе.** Сироп глюкозы, мальтодекстрин,
   декстроза, фруктоза, инвертный сироп — разные названия одного смысла. OFF
   считает добавки, но эту величину не считает. Это ключевая производная фича
   и самая наглядная часть демо.
2. **Разбор там, где таксономия не справилась.** LLM-корпус отбирается со
   смещением в `unknown_ingredients_n > 0` — то есть ровно туда, где парсер OFF
   бессилен. Это измеримый ответ на вопрос «зачем здесь LLM».
3. **Оценка качества по одному тексту состава**, без таблицы питательности —
   у многих продуктов её просто нет.

Парсер OFF при этом становится бесплатным rule-based baseline: в evals
сравниваются три системы, а не две — таксономия OFF, локальная 3B, облачная модель.

## Основная функциональность

- **Ingestion:** идемпотентное скачивание Parquet-дампа OFF, фильтрация и выборка
  корпуса через DuckDB, батчевая заливка в Postgres, инкрементальное обновление
  через дельта-экспорты.
- **Extraction:** LLM превращает `ingredients_text` в структуру по JSON-схеме:
  нормализованный список ингредиентов, тип каждого, число разных форм сахара,
  число E-добавок, аллергены, флаг нечитаемого состава. Промпт версионируется.
- **Evals:** CLI ручной разметки эталона (метки ставит только человек), раннер
  метрик precision/recall/F1, сравнение версий промптов и моделей, отчёты.
- **Analytics:** classic ML на готовых метках из базы — предсказание оценки
  качества и группы переработки; сравнение TF-IDF / эмбеддингов / LLM zero-shot
  по качеству, времени и стоимости.
- **Retrieval + RAG:** мультиязычные эмбеддинги профиля продукта, pgvector,
  гибридный поиск с фильтрами, ответы строго по найденным продуктам со ссылками
  на штрихкоды и отказом «не знаю» при отсутствии релевантного.
- **Agent + Serving:** агент с инструментами `sql_query` / `vector_search` /
  `lookup_barcode`, FastAPI, Telegram-бот, MCP-сервер. Без агентных фреймворков.

## Параметры корпуса

Заполнены по итогам уточнения; в код попадают через `.env`, не константами.

| Параметр | Значение |
|---|---|
| Языки составов | `en`, `ru`, `de`, `fr`, `pl` |
| Категории | снеки, кондитерка, напитки, молочное, завтраки |
| Аналитический корпус (classic ML) | 50–150 тыс. продуктов, метки из базы, LLM не нужна |
| LLM-корпус (extraction) | **1200 продуктов** (зафиксировано по факту прогона, ADR-017): 70% со смещением в `unknown_ingredients_n > 0` + 30% контрольная случайная подвыборка |
| Стратификация | по категориям и `nutriscore_grade` |
| Отсечки качества | `NOT obsolete`, пустой `data_quality_errors_tags`, длина состава ≥ 10 символов |

Точные размеры фиксируются по факту первого прогона выборки и обосновываются
в `DECISIONS.md`.

## Железо и вытекающие ограничения

RTX 3060 Laptop, 6 ГБ VRAM (подтверждено), 64 ГБ RAM.

- Модель извлечения — 3–4B в 4-битной квантизации. 7B+ не берём.
- Размер контекста задаётся **явно**: дефолт Ollama 4096 и подбирается
  динамически по VRAM, то есть молча режет вход. Ставим 8192 — расчёт по VRAM
  показывает запас (веса 1.9 ГБ + KV-кэш ~0.3 ГБ из 6 ГБ).
- Свободный JSON от 3B-модели ненадёжен → ограничение генерации параметром
  `format` с JSON-схемой, а не просьбы в промпте.
- LLM и эмбеддинги грузятся **последовательно**, с управлением `keep_alive`.
- Прогоны возобновляемые: прогресс в БД, перезапуск продолжает с необработанных.
- Перед полным прогоном — обязательный замер на 20 продуктах: секунды на продукт,
  токены, экстраполяция общего времени. Результат в отчёт.
- Под дамп нужно ~10 ГБ свободного места в `data/` (в .gitignore).

## Архитектура

Подробные архитектурные правила — в `.ai-factory/ARCHITECTURE.md`: раскладка
каталогов, правила зависимостей, порты для внешних систем, примеры кода
и антипаттерны.

**Паттерн:** Structured Modules (вертикальные слайсы по стадиям пайплайна).

### Заметки по архитектуре

Пять слоёв, поток данных строго в одну сторону:

```
дамп OFF (Parquet, HF)
  → DuckDB: фильтрация и выборка корпуса
  → Postgres: products_raw → products
  → Extraction (локальная LLM, JSON-схема) → product_extraction
  → Analytics (sklearn на метках из базы) → reports/
  → Retrieval (bge-m3 → pgvector) → RAG
  → Agent (инструменты, облачная модель) → API / бот / MCP
```

Решения, принятые на этапе подготовки:

- **Два адаптера источника, не один.** Полный дамп — Parquet с вложенными
  структурами, дельты — JSONL в MongoDB-форме с плоскими ключами. Обе формы
  сводятся к одной внутренней Pydantic-модели слоем нормализации.
- **Живой API OFF используется ровно в одном месте** — инструмент
  `lookup_barcode` у агента. Массовые данные только дампом: разработчики OFF
  прямо просят не выкачивать базу через API.
- **Трассировка за интерфейсом.** Отсутствие Langfuse не ломает пайплайн:
  по умолчанию no-op реализация.
- **Гейт evals в CI без GPU.** В репозиторий коммитятся предсказания модели на
  gold-наборе (не метки — их ставит человек). CI пересчитывает метрики из
  предсказаний и падает при просадке F1 > 3 пунктов. Полный прогон с облачной
  моделью — по `workflow_dispatch` и по расписанию.

Отложено сознательно: веб-фронтенд, дообучение моделей, экологические метрики
OFF, разбор упаковки, работа с изображениями продуктов.

## Схема данных (стартовая)

- `products_raw` — штрихкод (PK), исходный JSON отобранных полей, `imported_at`,
  версия дампа. Сырое не перезаписывается деструктивно.
- `products` — нормализованное: название, бренд, категории, страны, языки,
  БЖУ/соль/сахар на 100 г, `nutriscore_grade`, `nova_group`, флаги наличия данных,
  а также baseline-поля парсера OFF (`ingredients_tags`, `additives_n`,
  `unknown_ingredients_n`) — они нужны для сравнения в evals.
- `product_extraction` — результат LLM: нормализованный список ингредиентов, тип
  каждого (основа / сахар / жир / добавка / ароматизатор / консервант /
  подсластитель), число разных форм сахара, число E-добавок, аллергены, доверие
  модели, `model_name`, `prompt_version`, токены, время, `extracted_at`.
  Разбор мог не состояться: тогда `unreadable` поднят, а `skip_reason` говорит
  почему — `empty`, `too_long`, `output_limit` или `model_unreadable` (ADR-019).
  Записи с `unreadable` в аналитику не идут.
  Версионируется: у продукта может быть несколько извлечений разными версиями.
- `ingredients_dict` — канонические ингредиенты и алиасы по языкам.
- `product_embeddings` — вектор `halfvec(1024)` (bge-m3), `model_name`, HNSW-индекс.
- `runs` — журнал прогонов ingestion, extraction, evals.

## Нефункциональные требования

- **Конфигурация:** ни одной магической константы в коде. Всё через
  pydantic-settings и `.env`; в репозиторий только `.env.example`.
- **Логирование:** уровень через `LOG_LEVEL`, структурные логи, обязательные поля
  для прогонов — id прогона, модель, версия промпта, время, токены.
- **Тесты:** обязательны для парсинга, нормализации и извлечения. Внешние вызовы
  (Ollama, Anthropic, HTTP OFF) мокаются. Тест, ходящий в сеть, считается плохим
  тестом и не принимается.
- **Секреты:** не попадают в код, логи, отчёты и коммиты. Ключ Anthropic и
  `DATABASE_URL` — только из окружения.
- **Воспроизводимость:** фиксированные seed'ы для выборок и сплитов, версия
  дампа записывается вместе с данными, отчёты пересобираются одной командой.
- **Данные пользователей:** сообщения бота не хранятся дольше, чем нужно для
  ответа.

## Границы продукта

Соблюдаются на уровне формулировок в коде, README, ответах API и бота.

- Это **инструмент прозрачности состава, а не медицинский или диетологический
  советчик.** Система показывает, что написано в составе, и ссылается на данные.
  Не даёт рекомендаций по питанию, не строит диеты, не считает нормы под человека,
  не персонализируется под заболевания и цели по весу.
- Никаких оценочных ярлыков вроде «плохая еда» или «нельзя есть». Формулировки
  нейтральные и описательные: «в составе N разных форм сахара», «оценка по базе — C».
- Данные краудсорсинговые и могут быть неполными или неверными. Дисклеймер об этом
  и атрибуция ODbL — в README и в первом сообщении бота.
- Никаких целевых показателей калорий, дефицитов и трекинга съеденного.

## Метрики, которые проект обязан считать

Все числа берутся из кода, не из головы.

- F1 извлечения ингредиентов и их типов; динамика по версиям промпта.
- Сравнение трёх систем на одном gold-наборе: парсер OFF (rule-based),
  локальная 3B, облачная Claude — F1, секунды на продукт, стоимость полного прогона.
- Accuracy предсказания `nutriscore_grade` по тексту: TF-IDF vs эмбеддинги vs
  LLM zero-shot, вместе со временем и стоимостью каждого подхода.
- Accuracy предсказания `nova_group`.
- recall@5 семантического поиска на 20 запросах с эталонами.
- Доля утверждений RAG-ответа, подтверждённых найденными продуктами.
- Секунды на продукт локально; время и стоимость полного прогона локально и в облаке.
- Доля продуктов с пропущенными данными и её влияние на выводы.

Ожидаемый и самый ценный результат аналитики: TF-IDF окажется почти так же хорош,
как LLM, но в сотни раз дешевле. Если так — это пишется в README прямым текстом.
Умение не тащить LLM туда, где хватает логрегрессии, — главный сигнал проекта.
