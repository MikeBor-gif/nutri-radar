# Дорожная карта проекта

> Инструмент прозрачности состава пищевых продуктов на данных Open Food Facts:
> нормализация грязных многоязычных списков ингредиентов, поиск скрытых форм
> сахара и добавок, ответы со ссылками на конкретные штрихкоды.

Проект портфолийный: каждый майлстоун обязан заканчиваться **измеримым
результатом**, который владелец сможет защитить словами. Поэтому у пунктов
ниже стоит не «сделано», а что именно доказано и чем.

Правило 2 брифа: после каждого майлстоуна — остановка и ревью, следующий
не начинается по инициативе ассистента.

## Майлстоуны

- [x] **M0. Фундамент** — конфиг через pydantic-settings, Postgres с pgvector
      в Docker, миграции Alembic, health-check, каркас тестов, CI.
      Доказательство: миграции применяются с нуля, CI зелёный.
- [x] **M1. Ingestion** — дамп Open Food Facts, выборка через DuckDB, батчевая
      заливка в Postgres, инкрементальные дельты. Доказательство: **147 842
      продукта** в базе из 4,63 млн строк дампа, заливка 492 с (300 строк/с),
      повторный запуск дублей не создаёт.
- [x] **M2. Извлечение структуры состава** — локальная модель по JSON-схеме
      превращает грязный текст в структуру, появляется величина, которой в OFF
      нет: **число разных форм сахара**. Доказательство: 1187 разборов из
      корпуса 1200, 0 отказов модели, 1,13 формы сахара в среднем
      (после исправления счёта — ADR-035; изначально было 1,84),
      возобновляемость и отсутствие дублей проверены на живых данных.
- [x] **M3. Evals — закрыт частично.** Собран и проверен пайплайн: метрики
      precision / recall / F1 по ингредиентам и типам, точность числа форм
      сахара с разбивкой по языкам, отчёт приёмки, гейт в CI без GPU, БД
      и сети. Сравнены две системы (парсер OFF и локальная `qwen2.5:3b`);
      облачные выведены из объёма — нет ключа API (ADR-024).
      **Оценка качества извлечения не получена.** Эталон на 40 продуктах
      размечен моделью, а не человеком: правило 6 брифа нарушено по решению
      владельца проекта (ADR-026). Ошибки разметчика коррелируют с ошибками
      оцениваемой системы, поэтому числа годятся как проверка пайплайна
      и не годятся как оценка качества.
      **Оба вопроса M2 остаются открытыми навсегда** — на машинном эталоне
      обе гипотезы дают одинаковую картину. 2026-09-14 владелец отказался
      от ручной разметки, задача снята: эталон остаётся машинным. Инструмент
      разметки работает и лежит в репозитории, возврат стоит один вечер —
      но это решение владельца, а не запланированная работа.
- [x] **M4. Аналитика** — предсказание `nutriscore_grade` и `nova_group`
      по одному тексту состава на готовых метках из базы. Сравнение TF-IDF,
      эмбеддингов `bge-m3` и LLM zero-shot по точности **и стоимости**
      на одной подвыборке.
      Доказательство: **TF-IDF 68,4% против базлайна 44,3%** на Nutri-Score
      и **94,1% против 75,7%** на NOVA. Ожидание брифа оказалось слишком
      осторожным: локальная `qwen2.5:3b` не «сопоставима, но дороже», а
      **ниже базлайна на обеих задачах** (−15,8 и −2,9 пункта) при стоимости
      инференса в 400 раз выше. Эмбеддинги тоже проиграли символьным
      n-граммам. Проверено на двух версиях промпта и двух задачах; модель
      учит состав, а не язык — обгон держится внутри каждого языка. ADR-028.
- [x] **M5. Поиск и RAG — закрыт частично.** 146 350 профилей векторизованы
      `bge-m3` и лежат в pgvector (`halfvec(1024)`, индекс HNSW 381 МБ).
      Поиск отвечает за **34 мс**, RAG ссылается на штрихкоды и отказывается
      «не знаю», когда опоры нет, — отказ формируется кодом, а не просьбой
      в промпте.
      Доказательство: **47,0% выдачи обладает запрошенным свойством**,
      84,2% ссылок ведут в выдачу. Ингредиент вместе с категорией находится
      5 из 5 на трёх языках; ингредиент без категории и отрицание («без
      пальмового масла») проваливаются — измерено, а не предположено.
      **recall@5 из DoD заменён**: на корпусе с тысячами верных ответов
      он давал 0,0% у любой системы и мерил ошибку методики (ADR-029).
      **Эталон не человеческий** — 20 запросов составил ассистент, список
      верных ответов выводит SQL. Правило 6 нарушено осознанно.
- [x] **M6. Агент — закрыт частично.** Цикл «план → инструмент → наблюдение
      → ответ» написан руками и умещается в один файл; три инструмента,
      жёсткие лимиты, Langfuse в отдельном профиле. `lookup_barcode` —
      единственное место, где проект ходит в живой API OFF.
      Доказательство: на 10 вопросах локальная `qwen2.5:3b` выбрала
      **ожидаемый инструмент первым вызовом в 10 случаях из 10**, но дошла
      до ответа лишь в 20% — 14 повторных вызовов на 10 вопросов. Обвязка
      работает, удержание состояния между шагами — нет, и это ограничение
      модели, а не архитектуры (ADR-030).
      **«Агент решает задачи» не доказано и доказано не будет:** бриф задавал
      Sonnet 5, а 2026-09-14 владелец решил остаться на локальной модели —
      облачных прогонов в проекте нет (ADR-034). На 3B это не доказывается.
      Смена модели осталась строкой в `.env`, но пользоваться ею не будут.
- [x] **M7. Витрина** — FastAPI, Telegram-бот на aiogram, MCP-сервер
      поверх готовых слоёв. Точки входа тонкие: логики в них нет, вся она
      уже лежит в слайсах.
      Доказательство: сквозной прогон через HTTP — поиск за **6,9 с**
      с холодной моделью и **0,5 с** с загруженной, полный RAG-ответ
      за **13,4 с** при нуле выдуманных штрихкодов; карточка из корпуса
      отдаёт число форм сахара и имя модели разбора, карточка вне корпуса
      приходит из живого API без них; `docker compose up -d api`
      поднимается healthy.
      Атрибуция ODbL и дисклеймер стоят в первом сообщении бота и
      **ломают тест по подстроке**, а не ждут вычитки; оценочные ярлыки
      проверяются по всем текстам разом.
      **Бот не прогонялся против живого Telegram** — токена нет. Проверены
      хендлеры, маршрутизация, тексты, приватность логов и чтение штрихкода
      с картинки, 32 теста. ADR-031.

## Границы, действующие на всех майлстоунах

Записаны здесь, потому что нарушаются они обычно не решением, а по инерции:

- Массовые данные берутся **только дампом**. Живой API OFF дёргается ровно
  из одного модуля — `openfoodfacts.py`, по одному штрихкоду за вызов.
  Потребителей у него два: инструмент `lookup_barcode` у агента (M6)
  и карточка продукта вне корпуса (M7, ADR-031).
- Никаких оценочных ярлыков вроде «плохая еда». Формулировки описательные:
  «в составе N разных форм сахара», «оценка по базе — C».
- Ни целевых калорий, ни диет, ни персонализации под заболевания.
- Эталонную разметку для evals ставит человек, не модель.
- Новые зависимости — только по согласованию.
