# Базовые правила проекта Nutri Radar

> Кодовой базы пока нет, поэтому конвенции выведены из зафиксированного стека и
> раздела 4 брифа, а не из анализа существующего кода. По мере появления кода
> правила уточняются через `/aif-rules`.

## Именование

- Файлы и модули: `snake_case.py`
- Переменные и функции: `snake_case`
- Классы и Pydantic-модели: `PascalCase`
- Константы: `UPPER_SNAKE_CASE`, но только для настоящих констант — конфигурация
  идёт через настройки, не через константы модуля
- Таблицы БД: `snake_case`, множественное число (`products`, `product_extraction`)
- Alembic-ревизии: осмысленное `message`, не автогенерированная абракадабра
- Приватное: префикс `_`
- Async-функции **не** помечаются суффиксом `_async` — тип видно по `async def`

## Структура модулей

Пакет `src/nutri_radar/`, слои соответствуют потоку данных:

```
config.py     — pydantic-settings, единственный источник параметров
db/           — модели SQLAlchemy, сессии, репозитории
ingest/       — скачивание дампа, DuckDB-выборка, заливка, дельты
extract/      — JSON-схемы, промпты, вызов LLM, нормализация ингредиентов
evals/        — разметка, метрики, сравнение прогонов
analytics/    — модели на метках из базы, отчёты, графики
retrieval/    — эмбеддинги, векторный поиск, RAG
agent/        — инструменты и цикл агента
api/          — FastAPI
bot/          — aiogram 3
mcp_server/   — MCP поверх базы
```

Границы зависимостей — строго в одну сторону:

- `config` не зависит ни от чего внутри проекта
- `db` зависит только от `config`
- `ingest`, `extract`, `retrieval`, `analytics` зависят от `db` и `config`,
  но **не друг от друга** напрямую; общие типы выносятся в отдельный модуль
- `agent` зависит от `retrieval` и `db`
- `api`, `bot`, `mcp_server` — только точки входа: без бизнес-логики,
  вызывают слои ниже и форматируют ответ
- обратные зависимости запрещены: `db` ничего не знает про `extract`

## Конфигурация

- Ни одной магической константы в коде. Порог, размер батча, имя модели, размер
  контекста, лимиты агента — всё в `config.py` через pydantic-settings
- В репозиторий попадает только `.env.example`, актуальный по составу ключей
- Значения по умолчанию — в настройках, не разбросаны по вызовам
- Секреты читаются только из окружения и никогда не логируются

## Обработка ошибок

- Свои исключения наследуются от одного корневого `NutriRadarError`
- Внешние отказы (Ollama, Anthropic, HTTP OFF, БД) заворачиваются в доменные
  исключения на границе слоя — наружу не протекают `httpx.HTTPError` и подобное
- `except Exception` без повторного проброса запрещён; молчаливый `pass` в except
  запрещён
- Ретраи только для сетевых вызовов, с экспоненциальной задержкой и лимитом
- Валидация входов — Pydantic; ручные `assert` для проверки данных не годятся
- Битые записи в пайплайне не роняют прогон целиком: помечаются и пропускаются,
  счётчик попадает в `runs`

## Логирование

- Стандартный `logging`, уровень из `LOG_LEVEL`
- `print()` в коде библиотеки запрещён; в CLI вывод для человека — отдельно от логов
- Каждый прогон логирует: id прогона, модель, версию промпта, обработано/пропущено,
  время, токены
- Никаких секретов и полных сырых ответов LLM в логах уровня INFO

## Асинхронность

- SQLAlchemy 2.x в async-режиме, драйвер asyncpg
- Блокирующие вызовы не смешиваются с async-кодом: тяжёлый CPU (sklearn, DuckDB)
  живёт в синхронных функциях и запускается отдельно, а не внутри корутины
- Сессия БД не переиспользуется между задачами; область жизни сессии явная
- Массовые прогоны батчатся с ограничением параллелизма из настроек — Ollama
  на 6 ГБ VRAM не переживёт неограниченный веер запросов

## Тесты

- pytest + pytest-asyncio; файлы `tests/test_*.py`, функции `test_*`
- Обязательное покрытие: парсинг, нормализация, извлечение, фильтрация выборки
- **Тест не ходит в сеть.** Ollama, Anthropic, HTTP OFF — только моки
- Фикстуры данных — маленький синтетический Parquet и JSONL, лежат в `tests/data/`
- Для БД — отдельная тестовая база или транзакция с откатом; на dev-базе тесты
  не запускаются
- Проверяется поведение и граничные случаи, а не покрытие ради процента

## Git и коммиты

- Conventional Commits: `feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `chore:`,
  `perf:`, `ci:`
- Коммит на каждый логический шаг, не «работа за день»
- Ветки: `feature/<slug>` (см. `.ai-factory/config.yaml`)
- В коммит не попадают: `data/` (кроме `data/evals/gold.jsonl`), `.env`, дампы,
  веса моделей, содержимое `reports/`, если оно тяжёлое

## Документация решений

Каждое неочевидное архитектурное решение попадает в `DECISIONS.md` в формате
контекст → решение → альтернативы → последствия. Это не бюрократия: проект
портфолийный, и каждое решение придётся защищать словами.

## Приоритет правил

Правила брифа и этого файла **важнее** советов внешних скиллов. В частности:

- установленный скилл `fastapi-python` советует Redis для кэширования — Redis
  в проекте нет, добавление зависимостей требует согласования
- скиллы, советующие взять фреймворк (LangChain и подобные), игнорируются:
  отсутствие агентных фреймворков — сознательная часть демо
- при конфликте побеждает бриф, затем этот файл, затем скилл
