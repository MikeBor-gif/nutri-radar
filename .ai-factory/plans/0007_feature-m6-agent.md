## Roadmap Linkage

Milestone: **"M6. Агент"**
Rationale: план реализует ровно содержание пункта M6 карты — агент

## Согласованное решение: гоним на локальной модели

Бриф задаёт агента на Claude Sonnet 5, `ANTHROPIC__API_KEY` у проекта нет.
Владелец выбрал **вариант A**: механика строится, прогон делается на
`qwen2.5:3b-instruct-q4_K_M`, результат публикуется как есть.

Ожидание записано **до** прогона, чтобы потом не подгонять его под факт:
M4 измерил эту модель на этом же корпусе — 28,5% против базлайна 44,3%,
ответ «d» на 872 продуктах из 1000. Модель, не справившаяся с выбором из
пяти классов, вряд ли построит план из нескольких вызовов инструментов.
**Скорее всего результат окажется плохим, и это нормальный исход
измерения.** Плохое число, полученное честно, защищается словами; хорошее
число, полученное подгонкой, — нет.

Код пишется против порта `StructuredLLM`, поэтому смена модели на облачную
не потребует правок — только `LLM__PROVIDER` в `.env`.

## Цель майлстоуна и критерий готовности

**Цель:** показать, что агент с инструментами написан руками и понятен
целиком — это часть демонстрации, а не деталь реализации (правило 7 брифа).

**DoD:**

- Цикл агента написан руками: без LangChain, LlamaIndex, CrewAI и аналогов
- Три инструмента: `sql_query`, `vector_search`, `lookup_barcode`
- **Лимиты шагов и стоимости** — жёсткие, проверяемые тестом
- `lookup_barcode` — **единственное место**, где проект ходит в живой API
  Open Food Facts (раздел «Данные» брифа)
- Трассировка в Langfuse: видно план, вызовы инструментов и стоимость
- Прогон на наборе вопросов, результат в README **как есть**
- `pytest` зелёный без докера и без сети

**Чего здесь НЕТ:** мультиагентности, памяти между сессиями, планировщика
с ветвлением. Один цикл, три инструмента, жёсткие лимиты.

## Методические ловушки

1. **Инструмент `sql_query` — это выполнение SQL, сочинённого моделью.**
   Поверхность для инъекции и для случайного `DELETE`. Защита обязана быть
   структурной: read-only транзакция, единственный `SELECT`, обязательный
   `LIMIT`, таймаут, белый список таблиц. Просить модель «не делать плохого»
   защитой не является.
2. **Агент без лимита шагов зацикливается.** Слабая модель особенно
   склонна повторять один и тот же вызов. Лимит — не настройка удобства,
   а условие завершимости.
3. **Стоимость надо считать по факту, а не по плану.** Токены складываются
   по всем шагам, и агент, сделавший десять вызовов, стоит в десять раз
   дороже одного — это и есть цена агентности, её надо показать числом.
4. **Живой API OFF — ровно одно место.** Разработчики OFF просят не
   выкачивать базу через API. `lookup_barcode` берёт один штрихкод,
   с таймаутом и User-Agent проекта.
5. **«Агент справился» — не самооценка модели.** Успех определяется
   проверяемым признаком: дошёл ли до ответа, сослался ли на штрихкоды,
   уложился ли в лимиты. Спрашивать модель, справилась ли она, значит
   мерить самооценку — та же ошибка, что отвергнута в M5.

## Границы майлстоуна

**Не входит в M6:**

- Мультиагентность и передача задач между агентами
- Память между сессиями
- Планировщик с ветвлением и откатом
- FastAPI, бот, MCP — это M7

## Риски

| Риск | Признак | Что делать |
|---|---|---|
| `qwen2.5:3b` не справляется с выбором инструмента | агент зацикливается или отвечает без вызовов | это ожидаемый исход (см. выше), публикуется как есть; код готов к смене модели через `.env` |
| Модель сочиняет разрушительный SQL | `DELETE`, `DROP`, две команды в строке | защита структурная: read-only, один `SELECT`, белый список, тест на каждый случай |
| Агент уходит в бесконечный цикл | прогон не заканчивается | лимит шагов проверяется тестом, а не наблюдением |
| Живой API OFF отвечает медленно или падает | прогон висит | таймаут, «не найдено» как нормальный ответ, один штрихкод за вызов |
| Langfuse не поднят | агент падает на трассировке | трассировка деградирует до логов, проверяется тестом |
