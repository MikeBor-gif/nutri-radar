Ветка: `feature/m7-serving`
Создан: 2026-09-09

## Настройки

- Тесты: да — как во всех майлстоунах (правило 4 брифа)
- Логирование: подробное (DEBUG по умолчанию, уровень через `LOG_LEVEL`)
- Документация: да — обязательный чекпойнт, витрину открывает читатель README

## Roadmap Linkage

Milestone: **"M7. Витрина"**
Rationale: план реализует ровно содержание последнего пункта карты — FastAPI,
Telegram-бот на aiogram и MCP-сервер поверх готовых слоёв M1–M6, с атрибуцией
ODbL и дисклеймером в первом сообщении бота.

## Цель майлстоуна и критерий готовности

**Цель:** показать, что шесть стадий пайплайна доступны снаружи через три
точки входа, и что точки входа остались тонкими — вся логика уже лежит
в слайсах, витрина её только вызывает и форматирует.

**DoD:**

- FastAPI отдаёт: готовность среды, карточку продукта по штрихкоду,
  семантический поиск, RAG-ответ со ссылками на штрихкоды, ответ агента
- Telegram-бот отвечает на текстовый вопрос, на штрихкод строкой и на
  **фото штрихкода** (`zxing-cpp`)
- **Атрибуция ODbL и дисклеймер о краудсорсинговых данных — в первом
  сообщении бота (`/start`)**, а не в подвале. Прямое требование брифа
- MCP-сервер отдаёт наружу три инструмента агента через MCP Python SDK
- `docker compose up` поднимает базу и API; бот — отдельным профилем
- Формулировки нейтральные и описательные, оценочных ярлыков нет —
  проверяется тестом, а не вычиткой
- `pytest` зелёный без докера, без сети и без GPU

**Чего здесь НЕТ:** веб-фронтенда и Telegram Mini App (решение владельца
от 2026-09-09, ADR-031), аутентификации пользователей, хранения истории
диалогов, деплоя в облако.

## Методические ловушки

Записаны до реализации, чтобы не объяснять их постфактум.

1. **6 ГБ VRAM: две модели не живут одновременно.** `qwen2.5:3b` и `bge-m3`
   грузятся по очереди — в CLI это сделано руками через `await model.unload()`.
   В долгоживущем сервисе с параллельными запросами руками этого не сделать:
   два запроса начнут выгружать модели друг у друга, и латентность вырастет
   на порядок при нулевой нагрузке. Доступ к Ollama обязан быть
   **сериализован структурно**, а не «мы же не будем слать два запроса».
2. **Точка входа не содержит логики** (`ARCHITECTURE.md`). Три точки входа
   делают одно и то же — поиск, RAG, карточка. Соблазн — скопировать сборку
   конвейера из `retrieval/cli.py` трижды. Правильный ход: вынести сборку
   в публичную функцию слайса и перевести на неё сам CLI, чтобы копий стало
   не четыре, а одна.
3. **Карточка продукта берётся из локальной БД, а не из API OFF.** Главная
   величина проекта — **число разных форм сахара** — живёт только в
   `product_extraction` и в живом API её нет. Живой API остаётся фолбэком
   для штрихкодов вне корпуса и остаётся **единственным** местом похода
   в сеть (`lookup_barcode`).
4. **Нейтральность формулировок — свойство кода, а не дисциплины.** «Вредно»,
   «плохой состав», «лучше не есть» не должны появиться ни в одном шаблоне
   ответа. Проверяется тестом по списку запрещённых ярлыков на выходе
   форматтеров.
5. **Пользовательские данные не хранятся дольше ответа.** Бот не пишет в БД
   ничего о пользователе, фото декодируется в памяти и не ложится на диск,
   в логи не уходят ни текст сообщения, ни `user_id` в открытом виде.
6. **Бот без токена не должен ронять стек.** Токена в CI и на чужой машине
   нет. Отсутствие токена — понятная ошибка при старте бота и отдельный
   compose-профиль, а не падение `docker compose up`.
7. **Агент за HTTP — это минуты, а не миллисекунды.** На `qwen2.5:3b` цикл
   агента доходил до ответа в 20% случаев и тратил до 8 шагов (M6, ADR-030).
   Эндпойнт агента обязан иметь свой таймаут и честно возвращать «не
   уложился», а не висеть до таймаута клиента.

### Фаза 1: общий слой под тремя точками входа

- [ ] **Задача 1:** Зависимости и настройки. В `pyproject.toml`: `fastapi`,
      `uvicorn[standard]`, `aiogram>=3`, `mcp`, `zxing-cpp`, `pillow`

      agent_timeout_s) и `BotSettings` (`BOT__`: token как `SecretStr`,

      DEBUG. Пополнить `.env.example` с комментариями в стиле файла.
      **Логирование:** на старте писать в DEBUG выбранные хост/порт и
      факт наличия токена (`bool`, не значение).

- [ ] **Задача 2:** Сериализация доступа к Ollama — `llm/runtime.py`.

      обращения к моделям: эмбеддинги и генерация не выполняются
      одновременно, `keep_alive` и выгрузка управляются в одном месте.
      Параллелизм берётся из `OLLAMA__MAX_CONCURRENCY`, не из литерала.
      Это ловушка 1, и решается она структурно. *(зависит от 1)*
      **Логирование:** DEBUG на вход/выход из критической секции с именем
      модели и временем ожидания блокировки; INFO при выгрузке модели;
      WARNING, если ожидание блокировки превысило таймаут.
      Файлы: `src/nutri_radar/llm/runtime.py`, `src/nutri_radar/config.py`
- [ ] **Задача 3:** Единая сборка конвейера — `retrieval/pipeline.py`.
      Две публичные функции: «текст запроса → `SearchResult`» и «вопрос →
      `RagAnswer`», внутри — эмбеддинг, поиск, RAG, всё через `llm/runtime.py`.
      **`retrieval/cli.py` переводится на них**, чтобы копия сборки осталась
      одна, а не появились четыре (ловушка 2). *(зависит от 2)*
      **Логирование:** INFO на каждый вызов — длина запроса, число фильтров,
      найдено, латентность по стадиям (эмбеддинг / поиск / генерация)
      через `safe_extra`.
      Файлы: `src/nutri_radar/retrieval/pipeline.py`,
      `src/nutri_radar/retrieval/cli.py`
- [ ] **Задача 4:** Карточка продукта по штрихкоду. В `db/repositories/`
      добавить чтение продукта и его извлечения по коду (наружу — Pydantic,

      Формулировки описательные, оценочных ярлыков нет (ловушка 4).
      *(зависит от 1)*
      **Логирование:** INFO с кодом, источником данных и признаком
      «найдено/не найдено»; DEBUG на выбор ветки локально/фолбэк.
      Файлы: `src/nutri_radar/db/repositories/product.py`,

- [ ] **Задача 5:** Тесты общего слоя без сети и без БД: сериализация

## Границы майлстоуна

**Не входит в M7:**

- Веб-фронтенд и Telegram Mini App — решение владельца от 2026-09-09,
  фиксируется в ADR-031
- Аутентификация и личные кабинеты
- Хранение истории диалогов и любых пользовательских данных
- Деплой в облако, домен, вебхуки Telegram (бот работает на long polling)
- Дообучение моделей и любые правки слоёв M1–M6, кроме перевода
  `retrieval/cli.py` на общую сборку конвейера

## Риски

| Риск | Признак | Что делать |
|---|---|---|
| Две модели в 6 ГБ VRAM | латентность растёт на порядок при двух параллельных запросах | сериализация в `llm/runtime.py`, проверяется тестом (задачи 2, 5) |
| Логика уезжает в точку входа | `if` по домену в хендлере или в роуте | сборка конвейера одна, в `retrieval/pipeline.py`; CLI переведён на неё |
| Оценочный ярлык в шаблоне ответа | «вредно», «лучше не есть» в тексте бота | тест по списку запрещённых слов на выходе форматтеров (задачи 5, 13) |
| Утечка пользовательских данных в логи | текст сообщения или `user_id` в записи лога | middleware приватности + тест (задачи 10, 13) |
| `zxing-cpp` не читает фото с телефона | код не распознаётся на реальных снимках | понятная просьба прислать код текстом; ограничение размера файла; замер на нескольких реальных фото при приёмке |
| Агент висит на медленном прогоне | запрос к `/agent/ask` не возвращается | собственный таймаут эндпойнта и ответ «не уложился» (задача 8) |
| Бот без токена роняет `docker compose up` | стек не поднимается на чужой машине | отдельный compose-профиль для бота (задача 16) |
| Токен бота попадает в лог или коммит | значение видно в DEBUG-выводе | `SecretStr` + добавление в `secret_values()`, только `.env.example` в репозитории (задача 1) |
