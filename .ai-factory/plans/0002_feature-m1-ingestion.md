## Цель майлстоуна и критерий готовности

**Цель:** аналитический корпус Open Food Facts в Postgres. Массовые данные —
только дампом; живой API в этом майлстоуне не используется вообще.

**DoD из брифа:** аналитический корпус в базе, повторный запуск не создаёт
дублей, есть тесты фильтрации на маленьком синтетическом Parquet.

**Уточнённый DoD** (проверяется задачей 10):

- `ingest dump` скачивает 7,7 ГБ; повторный запуск **пропускает** скачивание
- `ingest select` заливает корпус; **повторный запуск не меняет число строк**
- Корпус попадает в вилку 50–150 тыс. продуктов, либо расхождение объяснено
  и зафиксировано в `DECISIONS.md`
- `ingest delta` применяет дельта-экспорты за доступное окно
- `pytest` зелёный без докера, `pytest -m integration` зелёный с поднятой БД
- Один и тот же продукт из Parquet и из дельты даёт **идентичный** `RawProduct`

## Контекст исследования

Источник: `.ai-factory/RESEARCH.md`, ADR-003 и ADR-004.

**Проверено фактически перед планированием:**

- URL дампа отдаёт `Accept-Ranges: bytes`, размер **7 702 435 530 байт (7,7 ГБ)**.
  Значит DuckDB читает файл удалённо через `httpfs`, и **разведку схемы можно
  сделать до скачивания**. Это снимает зависимость «сначала 7,7 ГБ, потом всё
  остальное» и позволяет качать дамп параллельно с работой над моделью
- HF отдаёт `302` на подписанный CDN-URL с параметром `Expires`. Для файла такого
  размера подпись может истечь посреди докачки → редирект нужно **переполучать**
  на каждой попытке, а не сохранять между ними
- Свободного места на диске: **119,8 ГБ**. Требуется ~10 ГБ — запас достаточный

**Что определяет всю структуру задач:**

- `ingredients_text`, `product_name` — это `LIST<STRUCT(lang, text)>`, а не строки;
  `nutriments` — список структур, а не набор колонок. Фильтр пишется через
  `list_filter`, а не `IS NOT NULL` (ADR-003)
- Дельты — **JSONL в MongoDB-форме** с плоскими ключами `ingredients_text_en`.
  Это второй адаптер, а не тот же ридер с другим путём (ADR-004)
- Парсер OFF уже разобрал состав: его поля забираются в `products` как baseline
  для сравнения в M3 и как критерий отбора LLM-корпуса (ADR-006)
- Имена колонок берутся только из
  `.ai-factory/references/openfoodfacts-parquet-fields.md`. `data-fields.txt`
  описывает CSV-экспорт, и половина имён оттуда в Parquet отсутствует

**Два вопроса, на которые отвечает только реальный файл** (задача 1, до
проектирования схемы):

1. Есть ли в `ingredients_text` служебная запись `lang = 'main'`
2. Точный набор значений `name` внутри `nutriments`, включая покрытие
   `fruits-vegetables-nuts-estimate-from-ingredients` — от него зависит ADR-005

## Границы майлстоуна

Сознательно **не входит** в M1:

- **Стратификация LLM-корпуса** и отбор по `unknown_ingredients_n > 0` — это M2.
  Здесь собирается только аналитический корпус; поля для отбора заливаются,
  но выборка по ним не делается
- Любые обращения к живому API OFF — он используется ровно в одном месте,
  инструмент `lookup_barcode` агента на M6
- Извлечение структуры состава, словарь алиасов ингредиентов — M2
- Эмбеддинги и `product_embeddings` — M5
- Таблицы `product_extraction` и `ingredients_dict` — M2

## Риски

| Риск | Признак | Что делать |
|---|---|---|
| Удалённое чтение через `httpfs` не заработает (редирект, подпись, прокси) | `ingest probe` падает на сетевой ошибке | путь отхода заложен в задачу 1: `--local` после `ingest dump`. Задача 2 от задачи 1 не зависит, поэтому блокировки не будет |
| Черновые теги категорий дают корпус вне вилки 50–150 тыс. | `--dry-run` показывает сильно меньше или больше | задача 10 предусматривает подбор тегов; таксономия OFF иерархическая, попасть с первого раза маловероятно |
| Подписанный URL истекает посреди докачки 7,7 ГБ | обрыв на середине, `403` при возобновлении | переполучение редиректа на каждой попытке — заложено в задачу 2 |
| Оборванная загрузка оставляет битый файл | следующий запуск принимает его за готовый | атомарная запись через `.part` + сверка размера — задача 2 |
| Фикстура Parquet проще настоящей схемы | тесты зелёные, реальный дамп падает | явное требование в задаче 8: та же вложенная схема `LIST<STRUCT>` |
| Построчные запросы вместо батчевых | заливка 100 тыс. строк идёт часами | тест на времени заливки 5000 строк с большим запасом — задача 9 |
| Старый дамп откатывает свежие данные | после повторной заливки поля стали старыми | upsert учитывает `rev`, проверяется тестом — задачи 6 и 9 |
| Отсутствующий нутриент превращается в `0` | в M4 нули уедут в обучение как настоящие значения | явная проверка в задаче 8: отсутствующий нутриент даёт `None` |
| DuckDB съедает всю память на большом файле | процесс убит ОС | `INGEST__DUCKDB_MEMORY_LIMIT` — задача 5 |
