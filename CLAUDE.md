# CLAUDE.md — Nutri Radar

Компактный свод правил для работы над проектом. Полная спецификация —
`.ai-factory/DESCRIPTION.md`, архитектура — `.ai-factory/ARCHITECTURE.md`,
детальные конвенции — `.ai-factory/rules/base.md`.

## Что это за проект

Разбор состава пищевых продуктов на данных Open Food Facts: нормализация грязных
многоязычных списков ингредиентов, поиск скрытых форм сахара и добавок,
предсказание оценки качества по тексту состава, RAG со ссылками на штрихкоды,
агент с инструментами.

**Проект портфолийный.** Его будут разбирать на собеседовании на позицию
ML/LLM-инженера. Отсюда приоритеты: инженерная аккуратность (тесты, миграции,
докер, CI), измеримое качество (метрики, а не «вроде работает»), и способность
владельца защитить словами каждое решение.

## Правила работы — важнее, чем код

1. **Один вертикальный слайс за раз.** Сначала «один продукт проходит путь от
   дампа до строки в БД», потом расширяем.
2. **Останавливайся после каждого milestone** и жди ревью. Не переходи к
   следующему по своей инициативе.
3. **Объясняй решения.** Альтернативы и причины выбора — в `DECISIONS.md`
   (контекст → решение → альтернативы → последствия).
4. **Тесты обязательны** для парсинга, нормализации, извлечения. Внешние вызовы
   мокаются. Тест, ходящий в сеть, — плохой тест.
5. **Никаких магических констант.** Всё в конфиг через pydantic-settings и `.env`;
   в репозиторий только `.env.example`.
6. **Не генерируй эталонную разметку для evals.** Метки ставит человек руками.
   Твоя задача — инструмент разметки и подсчёт метрик, но не метки.
7. **Не добавляй зависимости** без согласования. LangChain, LlamaIndex, CrewAI
   и аналогов в проекте нет — агент пишется руками, это часть демо.
8. **Коммит на каждый логический шаг**, Conventional Commits.
9. **Неоднозначное требование — спроси**, не додумывай молча.
10. **Секреты не попадают в код, логи и коммиты.**

## Ограничения железа

RTX 3060 Laptop, 6 ГБ VRAM, 64 ГБ RAM.

- Модель извлечения — 3–4B в q4. 7B+ не берём.
- **Размер контекста задаём явно.** Дефолт Ollama — 4096, подбирается динамически
  по VRAM, вход режет молча. Ставим 8192, запас по VRAM есть.
- Свободный JSON от 3B ненадёжен → параметр `format` с JSON-схемой, а не
  просьбы в промпте.
- LLM и модель эмбеддингов грузим **последовательно**, управляя `keep_alive`.
- Прогоны возобновляемые: прогресс в БД, перезапуск продолжает с необработанных.
- Перед полным прогоном — замер на 20 продуктах (секунды/продукт, токены,
  экстраполяция). В отчёт.
- Параллелизм запросов к Ollama — из настроек, не «сколько получится».

## Данные: Open Food Facts

- **Массовые данные только дампом.** Живой API дёргаем ровно из одного
  модуля — `openfoodfacts.py`, по одному штрихкоду за вызов, с таймаутом
  и User-Agent проекта. Потребителей у него два: инструмент `lookup_barcode`
  у агента и карточка продукта, когда штрихкода нет в корпусе (ADR-031).
  Третьего появиться не должно: новый поход в живой API — это правка
  этого модуля, а не новый `httpx`-вызов на месте. Разработчики OFF прямо
  просят не выкачивать базу через API.
- Дамп — **Parquet с HuggingFace** (`openfoodfacts/product-database`, split
  `food`, 4.63 млн строк). На `static.openfoodfacts.org` Parquet нет.
- **Имена колонок брать из `.ai-factory/references/openfoodfacts-parquet-fields.md`.**
  Файл `data-fields.txt` описывает CSV-экспорт, и половина имён оттуда в Parquet
  не существует (`nutrition_grade_fr` → `nutriscore_grade`, `sugars_100g` лежит
  внутри списка `nutriments`).
- `ingredients_text`, `product_name` — это `LIST<STRUCT(lang, text)>`, а не строки.
  `nutriments` — список структур, а не набор колонок. Фильтры пишутся через
  `list_filter`, а не `IS NOT NULL`.
- **Дельты — это JSONL в MongoDB-форме**, схема отличается от Parquet. Нужны два
  адаптера, сводящие обе формы к одной внутренней модели. Дельты не отслеживают
  удаление продуктов — это ограничение указывается в README честно.
- Дамп лежит в `data/` (gitignore), ~10 ГБ. Скрипт скачивания идемпотентный.
- **ODbL: атрибуция обязательна** — в README и в первом сообщении бота.

## Границы продукта — соблюдать в формулировках

- Это **инструмент прозрачности состава, а не медицинский или диетологический
  советчик.** Система показывает, что написано в составе, и ссылается на данные.
  Не даёт рекомендаций по питанию, не строит диеты, не считает нормы под человека,
  не персонализируется под заболевания и цели по весу.
- **Никаких оценочных ярлыков** вроде «плохая еда» или «нельзя есть».
  Формулировки нейтральные и описательные: «в составе N разных форм сахара»,
  «оценка по базе — C».
- Данные краудсорсинговые, могут быть неполными или неверными. Дисклеймер —
  в README и в первом сообщении бота вместе с атрибуцией ODbL.
- Никаких целевых калорий, дефицитов и трекинга съеденного.

## Чего не делать

- Не выкачивать базу через живой API — только дамп.
- Не тащить LangChain / LlamaIndex / CrewAI.
- Не заливать весь дамп в Postgres — только отфильтрованное подмножество.
- Не прогонять через LLM больше нескольких тысяч продуктов.
- Не делать веб-фронтенд.
- Не дообучать модели.
- Не хранить пользовательские данные из бота дольше, чем нужно для ответа.
- Не генерировать эталонные метки для evals.
